# Spec: the loop merges itself; the human is the escalation path

**Issue:** #64 · **Status:** Approved (approval = merge of this PR) ·
**Author:** athena (`evekhm-athena-app[bot]`) ·
**Open questions:** none

The accepted intent (`intent.md`, merged in 0b15da4) carried five Open
questions, a per-issue ceiling, and a monotonic-progress invariant to
this rung. No human was live in the design session, so each is
resolved below with its rationale grounded in the record rather than
posed back. **Any row in this table can be overruled by editing this
file at the merge gate** — the merge is the acceptance, so an edited
row *is* the decision.

Open question 1 lands as D1 and D2; question 2 as D3 and D4; question
3 as D7 and D8; question 4 as D9, D10 and D11; question 5 as D12. The
permanent merge policy the operator's 2026-09-04 interim starts from
is D5 and D6; the per-issue bound and the monotonic invariant are D13
and D14; `hold` is D15; self-dispatch is D16.

The interim policy in force since 2026-09-04 — merge when CI is green
and both reviewers' latest rounds carry an empty blocking set,
escalate otherwise — is a strict subset of D5. Everything below adds
the conjuncts an unattended writer needs that a human performing the
same check supplies from judgement.

## Decisions

| ID | Decision | Rationale |
|----|----------|-----------|
| D1 | **One policy for all five rungs: every rung's pull request is reviewed under REVIEW.md unchanged and merged by the same predicate (D5). There is no prose path and no code path.** Reading (b) of Open question 1 — prose merges on a structural check with no model verdict — is rejected as the *whole* gate and adopted as one conjunct of D5 (D2). | (a) is already what this repository does: PR #94 (an `intent.md`) and PR #96 (a `spec.md`) both drew full Argus and Atlas rounds with severities, IDs and ledgers, and REVIEW.md already provisions the case — "Where the change has no Decisions table (documentation changes, bootstrap PRs …), findings key to their own IDs and everything else in this protocol is unchanged" (REVIEW.md:317-320). The differing case the intent names — a well-formed, `Approved`, internally contradictory `spec.md` — is exactly what PR #96's round 1 caught (R1-1 found D9's premise false against D15 in the same file), so reading (b) would have shipped that contradiction to the build rung. The cost objection is real and is answered by the funnel rather than by a second policy: rounds 2 and 3 are verification-scoped (REVIEW.md:143-150), so a clean prose artifact costs two round-1 runs, not a loop. The stall objection — a reviewer blocks prose wrongly — is answered by D9: the round cap escalates, it does not wait. |
| D2 | **Severity for a prose artifact is the same closed `high` list (REVIEW.md:102-111), read through to the capability the artifact specifies: a finding is `high` if and only if the artifact **as written** would, when built, produce one of those five outcomes. No tier is added, no tier is redefined, and the `failure_scenario` field names the built consequence, not the sentence.** Separately and *not* as a finding, three structural facts are conjunct (9) of D5, checked deterministically by the merge gate: the rung's artifact exists at `intent/<n>-<slug>/<artifact>` for the row's `artifact` in `personas/lifecycle.json`; a `spec.md` carries `Status: Approved`; and a `spec.md`'s `Open questions` line reads `none`. | Extending the closed list would be a REVIEW.md amendment this issue did not ask for, and the list's whole purpose is that it is closed (REVIEW.md:56-61: "Blocking is a closed definition, not reviewer judgment"). Read-through needs no amendment because every prose rung's output is a specification *of* the capability the list already describes: "an unbounded loop, redispatch, or self-trigger" is the tier R1-1 correctly gave an intent that lacked a bound, on PR #94. The structural facts are conjuncts rather than findings because they are decidable by `grep` and a model verdict on them would be a model deciding a merge, which the intent forbids ("a model must not be the thing that decides a merge"). They also move a check that exists today from *after* the merge to *before* it: `lifecycle_advance.sh`'s Draft override currently posts a warning and refuses to advance a merged non-Approved `spec.md` (`docs/SPEC.md`, `lifecycle.labels`), which under an autonomous loop would be a merged artifact and a stopped ladder. |
| D3 | **The merge write is performed by `scripts/ci/merge_gate.sh`: deterministic bash + `gh` + `jq`, no model call, `DRY_RUN=1` printing every mutation instead of executing it, runnable locally by the same command CI runs.** It reads recorded state (the ledger, the labels, the check runs, the loop ledger) and writes at most one merge, one loop-ledger row, and — on refusal that escalates — one label swap and one comment. It never files a finding, never edits a ledger row's verdict, and never resolves a disagreement (D6). | The intent's determinism constraint and `lifecycle.labels`'s existing shape are the same shape, and the predecessor already computed this predicate in bash and jq. Reading (b) of Open question 2 — branch protection plus GitHub auto-merge — is rejected on the two charges the intent already prices: a required *approving review* would end the reviewers' comment-only authority (REVIEW.md:36-39, README:112), which is a policy reversal this issue did not ask for; and auto-merge re-evaluates checks, not labels, so a `hold` applied at 14:00 to a pull request whose checks went green at 13:59 does not stop it. A script that re-reads immediately before the write does (D15). |
| D4 | **The merge actor is a GitHub App installation distinct from all six personas and distinct from `GITHUB_TOKEN`, holding `contents: write` and `pull_requests: write` on this repository and nothing else. It has no persona source, no prompt, no model and no `personas/lifecycle.json` row — it is infrastructure, like `github-actions[bot]`.** Its key reaches the workflow by name (`MERGE_ACTOR_APP_PRIVATE_KEY`), never in argv and never in a prompt. Its entry lands in `scripts/auth/app_manifests.yaml`; `personas/**` is untouched. | Three things fall out at once. "No agent merges its own work" holds *by construction* rather than by a check, because the merge actor is never the author of anything (intent, Constraints). Least privilege is exactly the two scopes the intent names, on an identity that has no other duty. And the recursion fact decides it against the cheaper option: **an event generated by `GITHUB_TOKEN` does not start another workflow run**, so a merge performed with the default token would push to `main` and `.github/workflows/lifecycle.yml` would never run — the loop would merge and then stop dead at the label, which is the stall this issue exists to remove, reintroduced one layer down. An App installation token has no such suppression. Reading (a) of Open question 2 asked whether the merger is "a merger persona or an infrastructure identity"; it is the second, which is why `personas/**` and INTENT.md's persona cast do not change (#25, D10). |
| D5 | **`merge-eligible` is a conjunction of eleven facts, all read from recorded state, all re-read immediately before the write. Any false conjunct means no merge; a conjunct that cannot be evaluated means no merge (fail-closed).** (1) The base is the default branch and `head.repo.full_name` equals this repository — no fork (#25, D7; REVIEW.md:420-425). (2) Every required check run for the head OID is `success`; a pending, failed or missing required check is false, not "not yet". (3) Both reviewers have a verdict recorded against `Reviewed-head: <full-oid>` equal to the current head OID (D7). (4) The blocking set — open `security` plus open `high` rows — is empty (REVIEW.md:331-332). (5) The consensus axis is `agreed` and no blocking row carries a `dispute` verdict (REVIEW.md:335-339, D6). (6) Neither `hold` nor `blocked` is present on the pull request or on the issue it belongs to or closes (#25, D14; D15). (7) The merging identity is not the pull request's author (D4). (8) The pull request's issue is under both per-issue bounds (D13). (9) The rung's structural facts hold (D2). (10) The rung index is strictly greater than the highest rung index the loop ledger records as merged for that issue (D14). (11) The ledger carries a head marker and the head probe succeeded (REVIEW.md:346-348). | Conjuncts (2), (4) and (5) are the operator's 2026-09-04 interim policy restated mechanically; the other eight are the judgements a human supplied silently and an unattended writer must be given. Each is a fact already recorded by something that exists or is specified: (1) by the API payload, (2) by GitHub's own check API — REVIEW.md's `merge-ready` "is silent about CI, which is GitHub's own signal" (REVIEW.md:342), so CI is added *here* rather than by amending that definition, (3)–(5) and (11) by the recorder's ledger, (6) by the labels, (8) and (10) by the loop ledger (D13). Fail-closed on an unevaluable conjunct is the same rule `spec_check.sh` already applies to its own inputs and is what stops a gate from "running, deciding nothing, and reporting success" — itself an item on the closed `high` list (REVIEW.md:106-108). |
| D6 | **Disagreement is a recorded fact, never an inference: the pull request is in disagreement when the ledger carries a `dispute` verdict on any blocking row, or when the two reviewers' latest verdicts on the same Decision ID differ. The merge gate never adjudicates one — it refuses to merge and lets the funnel run; at the round cap it escalates (D9).** A disagreement over a non-blocking row is recorded and does not affect eligibility. | REVIEW.md already fires `disputed` "on an explicit dispute over ANY blocking row, because a contested high finding must stay visible even though it needs no routine peer verdict" (REVIEW.md:337-339), and already routes an unresolvable one to a human at three exchanges with both positions summarised (REVIEW.md:283-285). Both are consumed unchanged. Keying the second clause to Decision IDs rather than to diff hunks is REVIEW.md's own reconciliation rule (REVIEW.md:302-305), and it is what makes "the reviewers disagree" decidable by a script instead of by a reader. A merger that adjudicated would be a third reviewer with no protocol, and one whose verdict is a merge. |
| D7 | **Consensus that authorises a merge requires both reviewers to have posted a verdict against the current head OID. A missing verdict is not agreement.** A reviewer that dies, times out, abstains, or never starts blocks the merge; the item then reaches D8's deadline and escalates. `security` rows keep both reviewers' explicit AGREE, twice, unrelaxed (REVIEW.md:257-259). | Reading (b) — merge on one clean verdict plus no objection by a deadline — converts the dual-family design into a single-reviewer loop *precisely* when the second family is broken, which is the one circumstance the second family exists for. REVIEW.md's "where nothing is in scope, require no consensus" (REVIEW.md:352-354) is a rule about **rows**, not about reviewers: it says an item with no security rows needs no verdict on nothing, not that an item with no *reviewer* needs no review. The predecessor's "nine pull requests agreed and nothing could merge" is not reproduced under (a), because unlike the predecessor this resting state has a reachable exit — D8's deadline escalates it, which is exactly the fix REVIEW.md:352-355 prescribes. |
| D8 | **The stale-peer deadline escalates; it never authorises. When a pull request has one reviewer's verdict at the current head and the peer's row has been pending past the deadline, the item escalates (D9) instead of merging.** The clock is the ledger row's own pending timestamp (REVIEW.md:213-214, 220-222) and the check is the existing zero-token deterministic sweep (REVIEW.md:405-409) — no new clock is introduced. An explicit human request for the missing review (mention or manual dispatch, REVIEW.md:403-404) **resets** that row's deadline exactly once per head OID; a second request at the same head does not reset it again. | This is the whole content of the sub-question, and it is a question about *authority*, not about time: the clock already exists and already alerts, and reading (b) would grant it a new power — to authorise an irreversible write — that nothing in the record gave it. Reset rather than bypass, because an operator who asks for the missing review one minute before the deadline and then watches it merge without that review got the opposite of what they asked for; once per head rather than unbounded, because an unbounded reset is a human accidentally disarming the escalation by repeating a mention. Extend was rejected as reset-with-extra-arithmetic. |
| D9 | **An escalation is exactly two writes on the issue: the single `status:*` label is **swapped** for `status:review-stuck`, and one comment is posted stating both positions in two lines and naming the decision being asked for. Nothing else stops, nothing else is written.** The swap is one `gh issue edit` so the "at most one `status:*`" invariant is never transiently violated (`docs/SPEC.md`, `lifecycle.labels`). The comment carries a machine marker `<!-- escalation:<displaced-label>:<reason-code>:<head-oid> -->` where `<reason-code>` is one of `consensus-timeout`, `blocking-open-at-cap`, `dispute-at-cap`, `security-open`, `budget`, `non-monotonic`. The closed set of escalation causes is the intent's: consensus not reached within the round cap; a blocking finding still open at the round cap; `hold` or `blocked` present (recorded, not escalated — see D15); a budget gate tripped; a security-tier finding open at merge time. | Reading (a) — comment plus the existing label — is what AGENTS.md:240 and `docs/SPEC.md`'s `lifecycle.labels` already provision, and reading (b) would be a second reversal nobody asked for. The swap rather than an add is forced by the ladder: two `status:*` labels are corrupted state, and `lifecycle_advance.sh` responds to it by commenting and applying `hold` — so an escalation that *added* the label would halt the item through the corrupted-state path and blame the wrong thing. The displaced label goes in the marker rather than in prose because D10 has to restore it deterministically, and the resume protocol already refuses on `status:review-stuck` ("humans have taken over"), so the rung it displaced would otherwise be lost. `blocking-open-at-cap` is REVIEW.md's own round-3 branch adopted rather than reinvented (REVIEW.md:151-153): a pull request whose only open row is an agreed `high` is consensus-*agreed* and would otherwise be a resting state with no exit. |
| D10 | **Escalations that a new head can resolve clear themselves; the budget escalation does not.** On any subsequent evaluation where the escalating condition is gone — a full consensus at a new head with an empty blocking set, or the dispute withdrawn — the merge gate restores the displaced `status:*` from D9's marker, removes `status:review-stuck`, and proceeds. `reason-code: budget` and `reason-code: non-monotonic` clear **only** when a human changes the value in `config/execution.yaml` or removes the label by hand; no automatic evaluation clears them. `hold`/`blocked` are not escalations and clear with the label. | The two readings the intent names differ on an item the human answers in a comment and then ignores: self-healing resumes it, by-hand-only leaves it stuck forever — the same "every resting state needs a reachable exit" trap one rung out (REVIEW.md:352-355), and REVIEW.md:355-360 already prefers self-healing to cleanup for exactly this reason. The budget carve-out is not an exception to that principle but an application of it in the other direction: a spend gate that clears itself when the next evaluation happens is a spend gate that fails open, which is item two of the closed `high` list (REVIEW.md:105-106). A ceiling a human must raise is the only kind that is a ceiling. |
| D11 | **An escalation stops exactly one issue's ladder and nothing else. It is not repository-wide, it does not stop other issues, and it does not propagate to items that depend on the escalated one.** A dependent item that must not proceed is stopped by a human applying `blocked` to it — the existing act, the existing label. | Per-item is obviously right for a repository running several items and a global stop is obviously wrong; the only genuinely open case was the dependent item, and propagation is rejected because it requires the merge gate to hold a dependency graph. This repository states dependencies in prose inside intent documents (this one's Dependencies section included); a script inferring a stop from prose would be a parser deciding which work halts. `blocked` already exists, is already a refusal in the resume protocol, and is already a human's act. |
| D12 | **A human push to a pull request's head branch is an ordinary head change with no special standing: the recorded consensus stops covering the head (D5 conjunct 3), the reviewers re-review under the funnel, and the system merges when they agree again. REVIEW.md's merge-anytime escape hatch survives unchanged and is the override.** A human push consumes a review round from the per-pull-request cap (REVIEW.md, unchanged) and does **not** consume the per-issue rung-dispatch ceiling, which counts rung dispatches and not rounds (D13). | Reading (b) — a human edit ends the automation for that pull request — reintroduces the bottleneck through the back door every time the operator touches anything, which is the thing this issue exists to remove. The cost objection to (a) is the typo fix that pays for two model runs, and it is bounded by the funnel rather than by a policy: rounds 2 and 3 are verification-scoped, and the operator who does not want to pay even that merges the pull request themselves — "A human can merge or close any PR at any time, at any label state" (REVIEW.md:364), with the recorder filing one follow-up issue for whatever was open. Confirming that hatch survives is load-bearing: with `hold`, it is one of only two ways to override a stuck loop. |
| D13 | **An issue carries two bounds, both evaluated outside any single run, both fail-closed: a rung-dispatch ceiling and a spend ceiling.** They live in `config/execution.yaml` under a `loop:` block as `max_rung_dispatches_per_issue` (shipped default **12**) and `max_cost_usd_per_issue` (shipped default set by the operator in that file, with no in-repository literal duplicating it — #25, D8). The counter is a **loop ledger**: exactly one comment per issue, marked `<!-- loop-ledger:<issue> -->`, one row per rung dispatch carrying the rung, the dispatching event, the pull request, the merged head OID, the timestamp and the run's recorded cost. It is written by the same deterministic steps that dispatch and merge, is idempotent by `(rung, head-oid)`, and is the only counter — no run counts its own dispatches. Tripping either bound is a green exit that escalates under D9 with `reason-code: budget` (#25, D8). A ledger that cannot be read or parsed is a refusal to dispatch and to merge, not a zero. | The intent makes both mandatory in substance and leaves the shape here: both are specified because they fail differently — a cheap tight loop trips the count long before the dollars, and one expensive rung trips the dollars long before the count, and REVIEW.md:196-198 asks for a budget on the outermost loop, not for one metric. Twelve is five rungs plus headroom for the re-dispatches a healthy item actually takes (a rung whose pull request is closed and reopened, a placement retry), and it is small enough that the runaway in the intent's Problem section — advance, dispatch, merge, misidentify, repeat — trips within one working session rather than one weekend. The ledger is a comment because the counter must survive every run, be readable by a human and by the board (#68/#69) with no new store, and because the recorder's ledger already proves the shape works. |
| D14 | **Monotonic progress is a ratchet on the loop ledger, not on the label: for each issue the ledger records the highest rung index merged, and a dispatch or a merge at an index less than or equal to it is refused.** Rung index is the row's position in `personas/lifecycle.json` (the same ordering `lifecycle_advance.sh` already uses to rank competing transitions). A refusal escalates under D9 with `reason-code: non-monotonic` and writes nothing else. The ratchet is per issue, so a defect repair that re-enters at PLAN as a **new** issue (#57 spec, D18(b)) is unaffected. | This is the invariant that turns #72's failure scenario from a cycle into a single loud stop: a mis-written stage label sends the ladder backwards, and every per-pull-request and per-run cap is satisfied on every iteration, so nothing else in the system notices. The label cannot be the ratchet because the label is exactly what the defect corrupts; the ledger can, because it is append-only and keyed to merged head OIDs. Escalating rather than silently ignoring is the intent's rule for every bound ("tripping it stops the issue and escalates rather than failing silently"), and it is also the only way the operator learns the advancer is wrong. |
| D15 | **`hold` and `blocked` interrupt by being re-read immediately before every write — the merge, the loop-ledger row, and the next-rung dispatch — and never by cancelling an in-flight run (#25, D5/D13). Present on the pull request or on any issue it closes (#25, D14) means: discard the computed decision, write nothing at all, exit 0 green, and do not escalate.** A `hold` therefore stops the loop at the next write boundary at the latest, and a `hold` applied while a review run is in flight costs that run and no more. | The intent states this as a property and the mechanism already exists: this is #25's dispatch gate applied to one more write, plus trusted-posting rule 5, plus `lifecycle_advance.sh`'s own ordering, which checks `hold` before anything else. Green rather than red because a `hold` is the operator using the system correctly; silent rather than escalating because escalation is how the system asks the human a question, and a `hold` is the human having already answered one. This is the conjunct reading (b) of Open question 2 could not satisfy, and the reason D3 chose a script. |
| D16 | **The ladder dispatches its own next rung from inside the transition that writes the label: `lifecycle_advance.sh`, immediately after a successful `status:*` write and its comment, invokes the D17 placement adapter for the new stage's owner with the issue number and nothing else (#25, D16). No second workflow, no `issues: labeled` trigger, no new event.** `athena`, `daedalus` and `odyssey` move from `trigger: manual` to `trigger: repo-event` in `config/execution.yaml` — one line each (#25, D18/D19). A row whose `advances_to` is null dispatches nothing (D17). Dispatch is subject to D13, D14 and D15 in that order, before the adapter is invoked. | Same-run dispatch, rather than a workflow listening for the label, is forced by the same recursion fact D4 rests on: `lifecycle.yml` writes labels with `GITHUB_TOKEN`, and an `issues: labeled` event it generated would start no workflow — the ladder would advance and dispatch nothing, which is the stall moved rather than removed. It also keeps one writer and one ordering: the label, the comment and the dispatch are the same transition, so an item can never be dispatched for a rung whose label was not written. The trigger flips are the concrete half of the intent's "removing the merge click alone moves the stall", and #25 D18 already priced them at one line each. |
| D17 | **The review rung is terminal and owes no dispatch: review happens on the open pull request, before the merge, so `status:in-review` after a system merge is a state with no work owed.** The loop ledger's last row for the issue is written at that transition and marked terminal. Closing the issue remains the human's act and remains #57's Open question 2; nothing here closes, reopens or relabels a finished item (#57 spec, D8). `personas/lifecycle.json` is unchanged by this issue. | Under human merges the review rung was work: a human merged the code, then reviewers read it. Under this loop the reviewers' verdict is what *caused* the merge, so dispatching a review after the merge would pay two model runs to re-read a diff already reviewed at that exact head. The label still gets written, because it is the record that the implement rung completed and it is what the board reads. The per-issue bound stops accruing there by construction, since `advances_to` is null and no further dispatch is possible — which is the intent's worry about an issue that is never closed, answered without touching #57's decision. |
| D18 | **Autonomy is one config value, and turning it off does not undo the design: `loop.autonomous_merge: false` in `config/execution.yaml` makes the merge gate evaluate D5, write the loop-ledger row, and perform no merge and no dispatch — the predecessor's exact behaviour, a computed verdict informing a human's click.** The value is read fail-closed: unset, unparseable, or a missing file means `false`. | The intent's reversibility constraint asks that the ladder can still be run with human merges, and the workshop demonstrates both. A boolean read by the one deterministic step is the whole mechanism, and defaulting an unreadable config to "do not merge" is the same fail-closed rule as D5 — the failure that matters is merging when the operator meant not to, never the reverse. It also makes the change safe to land before its dependencies are all green: merged with the flag false, the gate is a recorder of merge-eligibility and nothing more. |

## Acceptance
