# Spec: Resilient Runner Completion and Merge Gate Check Handling

**Open questions:** none

## What is being built

This specification resolves artificial runner exit failures caused by transport stream interruptions and clarifies merge gate check run evaluation rules across eight binding decisions:

1. **Supersession of #43 D14 outcome resolution for headless execution**: When the harness child process exits 0 (`rc=0`), `scripts/ops/work.sh` inspects the decoded response payload for a terminal `WORK-RESULT:` line. If a valid `WORK-RESULT:` line is present, envelope status errors (such as stream interruptions) are demoted to a warning, and standard verdict exit code mapping executes.
2. **Harness-agnostic error demotion in `work.sh`**: Demotion of envelope status errors under child `rc=0` applies across all headless harnesses, logging the harness error message to stderr.
3. **Preservation of #64 D24 and #298 D3 check run evaluation in Conjunct 2**: In `scripts/ci/merge_gate.sh`, Conjunct 2 preserves D24 anti-spoofing identity rules intact. Check runs are never filtered or excluded by name. Foreign check runs on the head commit must conclude `SUCCESS` or `NEUTRAL`.
4. **Transient check failure remediation and retry integration**: Recovery from transient check run failures on pull request heads utilizes GitHub Actions retry mechanisms (`gh run rerun <run_id> --failed`), which update check run entries evaluated by #298 D3 deduplication. The merge gate does not trigger automated workflow retries.
5. **Terminal `WORK-RESULT` line extraction and parsing invariants**: Response extraction decodes the JSON payload, matches `^[[:space:]]*WORK-RESULT:`, selects the final line (`tail -1`), and validates the verdict token against `ok`, `refused`, and `blocked`.
6. **Warning logging and diagnostic transparency**: Demoted status errors emit an informative warning line to stderr containing the persona name, reported status, and error details.
7. **Scope boundary**: Authorizes modifications to `scripts/ops/work.sh`, `scripts/ops/tests/work_test.sh`, `scripts/ci/tests/merge_gate_test.sh`, `docs/SPEC.md`, and `intent/312-a-completed-runner/spec.md`. Excludes workflow files, personas, and `scripts/ci/merge_gate.sh`.
8. **Hermetic test requirements and contract assertions**: Specifies unit test scenarios in `scripts/ops/tests/work_test.sh` asserting stream interrupt demotion, verdict mapping, child exit code priority, and failure closed behavior.

```text
scripts/ops/work.sh                    # headless outcome resolution and error demotion
scripts/ops/tests/work_test.sh         # unit tests for stream interrupt demotion and exit codes
scripts/ci/tests/merge_gate_test.sh    # regression tests for Conjunct 2 check run evaluation
docs/SPEC.md                           # living spec update for headless launcher outcome mapping
intent/312-a-completed-runner/spec.md  # this specification
```

## Decisions

| ID | Decision | Rationale |
|---|---|---|
| D1 | **Supersession of #43 D14 outcome resolution for headless execution.** Amending #43 D14. In `intent/43-harness-agnostic-launch/spec.md`, decision D14 states: `status: "ERROR" (timeout, crash) → exit 1`. This rule is superseded for headless outcome processing in `scripts/ops/work.sh`:<br>When child exit code `rc == 0`, `work.sh` does not terminate immediately upon observing `status != "SUCCESS"`. It extracts the decoded response text (`response_text "$launch_harness"`) and inspects it for a terminal `WORK-RESULT: <ok\|refused\|blocked>` line.<br>1. If `rc == 0`, `status != "SUCCESS"`, and a valid terminal `WORK-RESULT:` line is present: `work.sh` demotes the envelope error to a warning logged to stderr (per D6) and evaluates the parsed `WORK-RESULT:` line per standard verdict mapping (`ok` exits 0; `refused` or `blocked` exits 2; unrecognised verdict exits 1).<br>2. If `rc == 0` and `status != "SUCCESS"`, but no valid terminal `WORK-RESULT:` line is present: `work.sh` logs `==> $launch_persona's session did not complete (exit $rc, status $status).` and exits 1 (fails closed).<br>3. If `rc != 0` (process crashed, aborted, killed by signal, or non-zero return code): `work.sh` always logs `==> $launch_persona's session did not complete (exit $rc, status $status).` and exits 1 (fails closed), regardless of whether a `WORK-RESULT:` line appears in the response stream.<br>4. If `rc == 0` and `status == "SUCCESS"`, but no `WORK-RESULT:` line is present: `work.sh` logs `==> $launch_persona's session exited cleanly but printed no WORK-RESULT line; the outcome was not observed.` and exits 1 (#43 D14 preserved). | In long-running sessions, `antigravity` (`agy`) can encounter a transport-level stream interruption at stream closure (`"error": "The stream was interrupted. Please continue the task you were working on."`). In this scenario, `agy` exits 0 (`rc=0`) and emits its full response envelope including all tool actions and the final `WORK-RESULT:` line, but flags `"status": "ERROR"`. Checking `[ "$rc" -ne 0 ] \|\| [ "$status" != "SUCCESS" ]` before reading the response caused completed sessions (such as Atlas on PR #309) to exit 1 artificially. Inspecting the decoded response whenever `rc == 0` allows verified completion to succeed while preserving fail-closed behavior for real process crashes (`rc != 0`) and truncated runs missing a result line. |
| D2 | **Harness-agnostic error demotion in `work.sh`.** Demotion of envelope status errors under child `rc == 0` applies across all headless harnesses. When `rc == 0` and a valid terminal `WORK-RESULT:` line is parsed from the decoded response payload, `work.sh` demotes any non-SUCCESS harness status to a warning regardless of the specific error string. The harness `.error` field is captured and logged to stderr per D6. | Restricting demotion to specific error strings (such as `stream was interrupted`) introduces brittle string coupling vulnerable to SDK version updates, localized messages, or upstream phrasing changes. Relying on process return code 0 combined with a parsed terminal `WORK-RESULT:` line provides robust outcome observation across harness variants while remaining fail-closed against unobserved outcomes. |
| D3 | **Preservation of #64 D24 and #298 D3 check run evaluation in Conjunct 2.** In `scripts/ci/merge_gate.sh`, Conjunct 2 preserves the anti-spoofing identity rule of #64 D24 and the deduplication logic of #298 D3 intact. Check runs are never filtered or excluded by check run name or context.<br>Quote #64 D24: *"The gate's own run is identified by identity and never by name: the one roll-up entry whose checkSuite.workflowRun.databaseId equals the evaluating job's GITHUB_RUN_ID. At most one entry is excluded, and every other entry counts whatever its name, merge-gate included."*<br>No exclusion by name is made for reviewer dispatch jobs (`argus via gh-actions`, `atlas via gh-actions`). Every foreign check run on the pull request head commit must conclude `SUCCESS` or `NEUTRAL`. | Filtering check runs by name creates an attack surface where an untrusted pull request could introduce a failing job named to match the exclusion list, bypassing Conjunct 2. Because D1 ensures that completed runner sessions exit 0 and conclude their check runs with `SUCCESS`, valid reviews will satisfy Conjunct 2 without special exemptions. Real runner crashes will conclude with `FAILURE` and correctly block merge gate until re-run. |
| D4 | **Transient check failure remediation and retry integration.** Recovery from transient check run failures on a pull request head is conducted via GitHub Actions retry mechanisms (`gh run rerun <run_id> --failed` or workflow re-dispatch), updating check run entries on the head commit.<br>Under #298 D3, `scripts/ci/merge_gate.sh` automatically evaluates the latest check run entry by `databaseId`. A successful re-run replaces an earlier failing check conclusion in Conjunct 2 without requiring an empty commit or push.<br>The merge gate script (`scripts/ci/merge_gate.sh`) does not initiate automated workflow re-runs; re-runs remain an operator and advisor remediation action. | Permitting the merge gate to automatically re-run failing workflows risks infinite retry loops on non-transient test or build failures, consuming execution quotas. Workflow re-runs require `actions: write` scope, which the merge gate does not possess. #298 D3 deduplication already provides an automated path to recognize completed retries on the existing head. |
| D5 | **Terminal `WORK-RESULT` line extraction and parsing invariants.** In `scripts/ops/work.sh`, `result_line` extraction parses the decoded response text (`response_text "$launch_harness"`) using line-anchored regex `^[[:space:]]*WORK-RESULT:`.<br>If multiple `WORK-RESULT:` lines appear in the decoded response text, the last line decides (`tail -1`), maintaining #43 D14's last-line-wins invariant.<br>The verdict token is extracted as the second whitespace-delimited field of the line (`awk '{print $2}'`).<br>Valid verdict tokens are strictly `ok`, `refused`, and `blocked`. Any other token or empty token is unrecognised, logs an error, and exits 1. | Decoding response JSON before matching prevents escaped newline bypasses. Anchoring regex matching avoids spurious matches within conversational text. Selecting the final result line allows agents to revise tentative conclusions before concluding. |
| D6 | **Warning logging and diagnostic transparency.** When a harness status error is demoted under D1 and D2, `work.sh` writes an explicit warning to stderr:<br>`==> warning: $launch_persona's harness reported status $status with error: $err; terminal WORK-RESULT observed, proceeding.`<br>Where `$err` is extracted from `.error` in the JSON payload (truncated to a single line and trimmed). If `.error` is null or absent, the warning reports `status $status (no error detail)`. | Transport stream interruptions must remain visible in execution logs and run artifacts for diagnostic tracking, even when demoted to non-fatal status. |
| D7 | **Scope boundary.** The implementation pull request for issue #312 may touch:<br>- `scripts/ops/work.sh`<br>- `scripts/ops/tests/work_test.sh`<br>- `scripts/ci/tests/merge_gate_test.sh`<br>- `docs/SPEC.md`<br>- `intent/312-a-completed-runner/spec.md`<br>The implementation pull request MAY NOT touch:<br>- `personas/**`<br>- `personas/lifecycle.json`<br>- `config/**`<br>- `.github/workflows/**`<br>- `scripts/ci/review_recorder.sh` or `scripts/ci/review_recorder.py`<br>- `scripts/ci/merge_gate.sh`<br>- `scripts/ci/lifecycle_advance.sh` or `scripts/ci/escalate.sh` | Preserves strict architectural boundaries. The defect originates in launcher envelope handling in `work.sh`. `merge_gate.sh` already possesses correct behavior under #64 D24 and #298 D3. |
| D8 | **Hermetic test requirements and contract assertions.** Contract test suite `scripts/ops/tests/work_test.sh` must include test scenarios verifying:<br>1. `AGY_RC=0`, `status: "ERROR"`, `error: "The stream was interrupted. Please continue the task you were working on."`, `response: "... WORK-RESULT: ok ..."` produces exit code 0 and logs the warning;<br>2. `AGY_RC=0`, `status: "ERROR"`, `error: "The stream was interrupted..."`, `response: "... WORK-RESULT: refused ..."` produces exit code 2;<br>3. `AGY_RC=0`, `status: "ERROR"`, `response: "..."` (no `WORK-RESULT:` line) produces exit code 1;<br>4. `AGY_RC=1` with `status: "ERROR"` and `WORK-RESULT: ok` in response produces exit code 1 (fails closed on non-zero child exit code);<br>5. `CLAUDE_RC=0`, `is_error: true`, `result: "... WORK-RESULT: ok ..."` produces exit code 0 and logs the warning.<br>All test scenarios must execute hermetically using existing stub fixtures without external network, token, or model calls. | Hermetic unit tests prevent regression in launcher exit mapping across all supported harnesses and failure paths. |

## Concerns

- **Preserving fail-closed semantics for unobserved outcomes**: The wrapper must strictly enforce that child exit code 0 is an absolute prerequisite for error demotion. A non-zero child exit code represents a process crash or signal abort and must never be converted to success.
- **Anti-spoofing integrity in Conjunct 2**: Upholding #64 D24 prevents pull requests from suppressing red checks by introducing jobs with reviewer names.
- **Diagnostic visibility**: Emitting a clear warning line to stderr ensures that intermittent transport stream issues remain observable in automation logs.

## Out of scope

- Modifying reviewer triggering or dispatch workflows in `.github/workflows/unattended.yml`.
- Modifying merge gate conjunct evaluation logic in `scripts/ci/merge_gate.sh`.
- Automated re-dispatch of failed workflows from within merge gate evaluation jobs.
