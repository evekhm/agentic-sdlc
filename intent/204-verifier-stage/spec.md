# Spec: the verifier seat — the review stage's verification protocol

**Issue:** #204 · **Status:** Approved (approval = merge of this PR) ·
**Author:** athena (`evekhm-athena-app[bot]`) ·
**Open questions:** none

This specification turns the accepted intent into commitments: the
review stage gets a written verification protocol with one owner in
the tree, the four deterministic ladder checks become a read-only CI
gate with tests before any prose describes them in the present tense,
the seat's interim powers are written once with their expiry, and the
seat's identity question is closed. It answers the intent's four Open
questions in D16 (where the interim authority is recorded), D5 (gate
width), D12 (where the pre-merge checks live) and D15 (the seat's
identity).

## Decisions

| # | Decision |
|---|---|
| D1 | **The verifier is the review stage, executed by the existing `argus` persona's protocol; no new persona, no stage-enum change.** `personas/lifecycle.json` derives a stage's owners from every `personas/*.yaml` whose `stage` list contains it, so argus and atlas both compile from the review-stage sources and both inherit the protocol through `personas/skills/review-protocol.md`, which both already declare. Neither gains a verb: both stay `github_write: "comments"`. This is scoped to seat 2 only; #199 adds `personas/nestor.yaml` for the advisor seat (its D1) and that is not in tension — the advisor seat needs an actor, the verifier seat needs a protocol. No artifact of this issue restates a persona count. |
| D2 | **The durable protocol is one section of `REVIEW.md`, titled `## The verification protocol`, inserted immediately before `## Severity tiers`, and it exists exactly once in the tree.** It states one precondition and eight ordered steps, each with a stable ID a verdict and an acceptance test can cite. **V0 (precondition)** — a reviewer never reviews a change containing a commit it authored; prescribing a fix in a review or a fix prompt does not disqualify it from reviewing the fix. **V1 Distrust the summary** — the pull-request body and the implementer's handoff are claims; nothing in them is cited as verification. **V2 Independent findings** — read the whole diff against the merge base and the spec's Decisions table; file findings per the existing ID, tier and Decision-keying rules, formed before reading any peer's. **V3 Re-run every gate** in the pull request's worktree at the reviewed head: the suites the issue or plan names, `scripts/ci/sanitize_check.sh`, `scripts/ci/spec_check.sh` when a behavior-bearing path changed, `python3 scripts/sync_agents.py --check` when `personas/` or `config/` changed; the verdict cites each command and its exit status. **V4 Reproduce, never read** — re-run every reproduction command, recompute every derived value against the live system, and provenance-check every pasted "before" output: output that cannot be produced from the merge base is a finding, at whatever tier the closed lists assign its consequence (this protocol adds no tier). **V5 Mutation-test when coverage is the point** — for any change whose claim is a test or a guard, reintroduce the defect (or remove the fix) and observe the suite go red; a suite that stays green is a finding; read which line the passing assertion matched, not that it printed PASS. **V6 Ladder checks** — confirm the ladder gate (D5) is green at the reviewed head; each red line is a finding; a reviewer never waives one by hand; for a head whose checks predate the gate, run the gate script locally and cite its output. **V7 Read the decision line behind every reviewer check** at the reviewed head, classified per D13, handled per D14. **V8 The verdict** — one comment per REVIEW.md's existing verdict format, carrying an evidence block of exactly one line per step, `V<n>: <pointer>` (a command with its exit status, a run id with its job id, a commit sha, a comment link) or `V<n>: n/a — <reason>`; a verdict missing a step's line is not a verdict and is not delivered. Every round's verdict carries the block; in verification rounds the steps' scope is the round's scope per the funnel. Rationale: the intent's finding is that the rung had a politics and no protocol; a protocol that lives in three documents is three protocols, so the steps are written here once and everywhere else points by ID. |
| D3 | **`personas/skills/review-protocol.md` gains application rules and no step text.** It adds, as bullets under its existing "Application rules": run `REVIEW.md`'s verification protocol V0–V8 in order, and owe a verdict only when V8's evidence block is complete; V7 is satisfied by the dispatch's own decision line and never by inference (D13), and an unreadable decision line is recorded per D14, never guessed; the ladder gate is read, never re-derived and never waived (V6). The skill names a step by its ID and at most one clause; it never reproduces the list. Rationale: `scripts/sync_agents.py` inlines every declared skill verbatim into the compiled briefs and `--verify` asserts the text survived, so this file is the channel by which the protocol reaches every runtime; keeping it to pointers keeps `REVIEW.md` the one owner. |
| D4 | **The review rung's `dispatch_brief` in `personas/lifecycle.json` points at the protocol.** Its text becomes: `Run REVIEW.md's verification protocol (V0-V8) against the open pull request at its head; post findings and a verdict with the evidence block, never a merge.` The compiler renders this line into the ladder section of every brief that declares `resume-protocol.md`, and `scripts/ops/work.sh` prints it at dispatch, so no second copy is written. Rationale: today the rung's entire instruction is one line that names no protocol. |
| D5 | **The mechanized gate is narrow: exactly four ladder checks, run pre-merge, reads only.** (a) closing-keyword count per D7; (b) branch per D8; (c) claim identity per D9; (d) commit authors per D10. It runs as one added job in `.github/workflows/ci-gates.yml` on `pull_request` events only (like `spec-check`, it needs a pull request), with job-level `permissions: contents: read, issues: read, pull-requests: read` and `GH_TOKEN: ${{ github.token }}` — the repository is private, so the workflow's file-level `contents: read` alone cannot read an issue thread; the added scopes are read scopes and the job holds no secret and no write permission. It is a deterministic script runnable locally by the same command CI runs, taking a pull-request number and `GITHUB_REPO` like its siblings. It writes nothing: no label, no comment, no `hold` (the stage advancer is the single writer of the circuit breaker), and it never posts. Output contract: one line per check, `<check>: PASS`, `<check>: FAIL — <reason>` as `::error::`, or `<check>: N/A — <reason>` as `::notice::`; exit 0 iff no line is FAIL. Whether the job is a required status check is a repository setting outside the tree and outside this spec; `REVIEW.md`'s merge-ready remains silent about CI. The #191 fake-green class (asserting a green check did real work) stays out: it has its own dispatch, and this issue leaves job-log reading prompt-enforced (V7). Answers Open question 2. |
| D6 | **Resolution, applicability, regime.** Step 0 resolves the pull request to its issue exactly as `scripts/ops/work.sh` does — a closing keyword and same-repo `#<n>` in the body first, then the `<actor>/<n>-<slug>` head branch — by calling the shared library (`closing_refs`, `branch_issue` in `scripts/ops/lib/github.sh`), never a second parser (D12). A pull request that resolves to no issue is *untracked*: the gate reports `untracked pull request` as a notice and exits 0. A resolved issue is classified into one of two **regimes** from its labels, mirroring the dispatcher's stage derivation: more than one `status:*` label is corrupted state and every check FAILs naming the labels (never a guess, never `hold`); a `status:*` label that names no rung in `personas/lifecycle.json` FAILs the same way. **Ladder regime**: exactly one rung label whose row has `advances_on` `"artifact"` or `"merge"`, or no `status:*` label with `intent:new` present (the first rung, as `work.sh` derives it). **Repair regime**: no `status:*` label and no `intent:new` (the defect-repair path, `work.sh` refusal (f), #82), or the terminal rung (`advances_on` null) — at the terminal rung the ladder has nothing left to advance and any pull request against the issue is a fix that completes it (observed: #172, #137). A pull request whose head repository is not this repository, or whose head repository is deleted, FAILs (b), (c) and (d) with one line — persona branches exist only where persona tokens can push, and a fork is never read as an identity claim (the same stance as the advancer's fork gate); (a) is still evaluated. `hold` on the issue or the pull request does not suppress the gate: it makes no write for `hold` to forbid. |
| D7 | **Check (a): the closing-keyword count is a per-regime expectation, counted the way GitHub counts, with one declared escape hatch.** Let C be the number of distinct same-repo issues the body closes per `closing_refs` — every keyword GitHub honours (`close`, `fix`, `resolve` and their `-s`/`-d` forms, case-insensitive), wherever it appears in the body: the gate counts what GitHub will act on at merge, not what the author meant, and GitHub does not read negation. C > 1 always FAILs, naming both numbers (two units of work). **Ladder regime**: expected C = 0 — AGENTS.md "Working the tracker" step 4 (no pull request in the five-rung flow carries `Closes #<n>`; the human closes) and #57 D2/D9 (the advancer turns red when the implementing pull request closed its issue); C = 1 FAILs with the message that the ladder's pull requests carry no closing keyword, and no marker waives it — a keyword there is never deliberate. **Repair regime**: three outcomes. C = 1 → PASS. C = 0 with a body line `Closing-keyword: none — <reason>` (non-empty reason) → PASS, the reason echoed in the gate's line — a deliberately partial fix is legitimate, and the marker is the machine-readable trace that it was deliberate; it is the same idiom `scripts/ci/spec_check.sh` already accepts for its own obligation (`Spec-impact: none — <reason>`), reused so the tree has one convention for "knowingly not satisfying this gate, and here is why". C = 0 with no marker → FAIL; a marker with no reason → FAIL (spec_check's rule); a marker alongside C ≥ 1 → FAIL as a contradiction. The real shape this pins, described accurately: PR #185 targets #74, which sits at `status:implementing` — the implementing rung, whose merge advances to `status:in-review`; the terminal rung is review (`personas/lifecycle.json`), so #185 is a ladder-regime pull request and the rule is C = 0. Its author omitted the keyword deliberately and said so in prose — a sentence of the form "This PR does not" followed by the keyword and the issue number — but that sentence is itself a live closing reference, because neither GitHub nor `closing_refs` reads negation. At 07:29 UTC on 2026-09-07, GitHub's `closingIssuesReferences` for #185 listed #74; the author reworded the sentence at 07:43 UTC and the list is now empty. This spec therefore pins the SHAPE, not the live pull request: a ladder-regime body carrying a negated keyword FAILs (a) naming the reference the gate counted, the same body with the sentence reworded PASSes, and the marker alone would not rescue the first case, because the stray reference would still be there. Acceptance item 7 states it as a fixture for exactly this reason — a fixture keyed to a live pull request's current body is a test that a third party can repair out from under the suite, which is what happened here within fifteen minutes. Two gaps, then, not one: a deliberate omission with no machine-readable trace (the marker closes it, in the regime where omission is a choice) and a negated keyword the parser cannot see (rewording closes it, and the gate says which reference it counted). The intent's framing of #185 as "carries no closing keyword" is corrected here; the spec follows GitHub's parser and the lifecycle source. |
| D8 | **Check (b): the head branch matches the persona convention.** Parse the head branch with the same branch pattern the shared library uses (`<actor>/<n>-<slug>`, zero-padding of `<n>` tolerated and compared as decimal). If `<actor>` is not the name of a `personas/<actor>.yaml` with `kind: persona`, the pull request is a *non-persona* pull request: in the repair regime (b), (c) and (d) are N/A and the gate can pass (a human's fix branch, e.g. the `eva/…` shape already on `main`); in the ladder regime (b) FAILs — the ladder's pull requests come from persona lanes, and a hand-driven bootstrap dispatch is made under the persona identity per AGENTS.md. For a *persona* pull request: `<n>` must equal the resolved issue (a body closing #137 on a branch `odyssey/74-…` FAILs here, whichever way the resolver went); in the ladder regime the persona's `stage` list must contain the issue's derived stage (the dispatcher's owner set); when the issue's rung has `advances_on` `"merge"`, exactly one `intent/<n>-*/` directory must exist in the pull request's head tree and `<slug>` must equal its slug — zero or two directories FAIL, a mismatch FAILs — because that is precisely the advancer's D15/D17 test, and a near miss found after merge means "the rung must be advanced by hand" (#57 D17); the gate predicts that verdict before the merge. |
| D9 | **Check (c): the claim is posted under the persona's App identity.** Persona pull requests only. The claim is the LAST comment on the issue's thread whose body opens with `Claim`/`Claiming` (the structured line AGENTS.md step 2 prescribes, matched by the same pattern `work.sh` uses; prose merely containing the word is not a claim). Its **author login** — never a name read out of the body, which is an unauthenticated string — must equal `authority.identity` in `personas/<actor>.yaml` for the branch's actor. No claim comment FAILs (a persona pull request on an unclaimed issue); a different author FAILs naming the login (the #191 shape, a bare operator login); the last claim being another persona's FAILs (the branch's actor does not hold the mutex); an identity whose literal value is `TBD` FAILs naming the persona — #199 D11's interim is thereby visible on every pull request it produces rather than exempted. |
| D10 | **Check (d): every commit is authored by the persona, with the numeric id verified against the API.** Persona pull requests only. For every commit in the pull request's own commit list (`repos/{owner}/{repo}/pulls/{n}/commits`, paginated; merge commits included, no exemption — a branch updated by a human login through the web merge button is a human commit on a persona lane, and the remedy is to redo the update in the persona's session), the commit's **author email** must equal `<id>+<identity>@users.noreply.github.com`, where `<identity>` is the branch persona's `authority.identity` and `<id>` is the `.id` GitHub returns for `users/<identity>` (URL-encoded, fetched once per persona per run). Both halves bind: an email carrying another persona's id or another persona's login FAILs. A lookup that returns a non-success status or a non-integer id FAILs naming the lookup — no read fails open. Author name and committer are not checked (stated so nobody widens it by assumption). The two real shapes: PR #188's commit `a736d92d`, authored `181938210+evekhm-odyssey-app[bot]@users.noreply.github.com` — id `181938210` does not exist, the login's id is `323814131`; and this issue's own intent commit, first written with `219526918+evekhm-athena-app[bot]@…` by an author who had just documented the defect (the id is `323812244`; corrected before push). A rule a well-informed author violates within minutes of writing it down is code, not prose. |
| D11 | **Tests are hermetic, run in CI, and pin the real defects.** `scripts/ci/tests/<ladder gate>_test.sh` follows `scripts/ci/tests/lifecycle_advance_test.sh`: a stub `gh` first on PATH answering reads from fixtures, an invocation log, a write log that must stay empty, no network, no token. Fixtures at minimum: (1) PR #188's shape — a persona commit whose email id is not the id the `users/` stub returns → FAIL (d); (2) a repair-regime issue (labels `bug` only) with a body carrying no closing reference and no marker → FAIL (a); (3) PR #185's shape — a ladder-regime issue at the merge rung whose body contains "does not close #<n>" → FAIL (a); the same body with the sentence reworded → PASS (a); the same body plus a `Closing-keyword: none` marker, sentence unchanged → still FAIL (a); (4) two closing references → FAIL (a) naming both; (5) repair regime, C = 0, `Closing-keyword: none — <reason>` → PASS (a) with the reason echoed; the marker with no reason → FAIL (a); the marker alongside one reference → FAIL (a); (6) claim authored by a non-persona login → FAIL (c); no claim → FAIL (c); identity `TBD` → FAIL (c); last claim by another persona → FAIL (c); (7) non-persona branch on a repair-regime issue → (b)(c)(d) N/A, exit 0; the same on a ladder-regime issue → FAIL (b); (8) merge-rung slug mismatch and two-folder cases → FAIL (b); (9) head repository not this one → FAIL (b)(c)(d), (a) evaluated; (10) `users/` stub answering non-success → FAIL (d); (11) untracked pull request → notice, exit 0; (12) a fully conforming persona pull request in each regime → exit 0 with four PASS lines; (13) every scenario asserts the write log is empty. Where a scenario's expected string is a rung label or a persona identity, the test reads it from `personas/lifecycle.json` or the persona source at run time rather than hard-coding it, as the advancer's tests do. |
| D12 | **One owner in code for every rule the gate applies, and the gate's tests execute in CI; the file is the plan's discovery step.** Today the closing-keyword parse has exactly one owner, `closing_refs` in `scripts/ops/lib/github.sh` (the dispatcher's resolver calls it; `scripts/ci/lifecycle_advance.sh` parses no keyword at all — its D9 red reads the consequence, a closed issue at the merge rung). The branch pattern lives in that library (`branch_issue`) and, pre-existing, inline in the advancer; the claim pattern and the stage-from-label derivation live inline in `scripts/ops/work.sh`. The gate adds **no new copy** of any of these: it sources the shared library, and where a rule it needs is inline in one caller today (claim pattern, stage derivation), the plan factors it into the library so that caller and the gate both read one definition. The advancer's own tested inline pattern is not modified by this issue. Second criterion, weighed by the plan: `.github/workflows/ci-gates.yml` runs exactly three test suites today (`scripts/ops/tests/execution_test.sh`, `placement_test.sh`, `post_test.sh`); `scripts/ci/tests/lifecycle_advance_test.sh` and `scripts/ops/tests/work_test.sh` are local-only. The new checks' tests must run on every pull request, so extending `lifecycle_advance.sh` carries a cost the sibling option does not — the extended script's whole suite must then be wired into the job — and the plan states which it pays. Whether the gate is a new script under `scripts/ci/` or a `--pr` mode of `lifecycle_advance.sh` is decided by the plan's first task, which must enumerate each rule with its current owner (`file:function`), name the placement with its reason against both criteria, and name the workflow step that runs the tests; the acceptance list below is identical under either placement. Answers Open question 3 (AGENTS.md, "Never duplicate code"). |
| D13 | **V7 is satisfied only by the dispatch's own decision line.** For each reviewer check at the reviewed head, the reviewer reads the job's log and classifies it as exactly one of: **reviewed** — a review from that reviewer is posted at this head (its `Reviewed-head:` marker or signed header), read the findings; **refused by design** — the dispatch log's last line begins `refused:` and the step emitted `<persona> refused #<n> (exit 2) — not worked, by design:` as a notice, record the reason verbatim, and the seat's own review is the only review of record; **hollow** — conclusion success, no `refused:` line and no review posted at this head, record it on #191 with run id, job id and head sha (the check is not evidence and nothing about the change is blamed for it); **failed** — a non-success conclusion, record the error line. Duration, comment count and the job-steps API's step conclusions never classify: they separate *reviewed* from *not reviewed* and cannot separate *refused by design* from *refused hollowly*. Evidence: PR #206's argus check went green in 22 seconds with zero comments and was reported as hollow; the completed log read `refused: in-progress on #204 is held by athena` — a by-design ownership refusal. The correction is on record at #191. |
| D14 | **When the decision line cannot be read, V7 blocks; it never assumes.** `gh run view --job <id> --log` refuses while any sibling job of the run is pending, and the job-steps API returns step conclusions but not the decision text. Two roles, two rules. An **unattended reviewer** (a job inside the run in question) classifies only the reviewer checks already complete at the reviewed head, records the rest as `V7: pending — run <id>` and proceeds with its own V1–V6, V8; it never waits on a sibling and never infers. **Whoever declares merge-readiness** — the human seat today (D15/D16), the consensus recorder after #64/#151 — does not declare it until every reviewer check at the head is classified per D13; an unreadable log withholds the AGREE, the seat re-reads when the run completes (bounded by the reviewer job's own timeout in `.github/workflows/unattended.yml`), and a run that cannot complete is recorded as a #191/#167 instance, not waived. The human escape hatch is unchanged: an explicit operator merge over an unresolved V7 is legitimate and the merge comment says so and names the run (`merging per operator direction; V7 unresolved for run <id>`), the same shape PLAYBOOK already requires for a deferred row. Rationale: assuming *pass* re-opens the exact channel #191 exists to close; assuming *hollow* produced a wrong finding on #206; blocking costs at most one job timeout. |
| D15 | **The verifier seat is the human operator, named in the record; it gains no bot identity.** No persona source, no `authority` block, no App, no schema change. Grounds: `REVIEW.md` makes a human the sole merge authority on every path, and giving a bot the verbs `approve`/`merge`/`close` breaks "authority is a vocabulary"; that is also the tree's current state, not an aspiration — no `gh pr merge` exists under `scripts/` or `.github/workflows/`, and `docs/SPEC.md` lists `review.automation` under "Agreed, not yet built" (#8/#9) with the reviewer execution bindings inert until then, so the seat's merge is a human hand on the button because no other mechanism exists; the only pressure for an identity came from `scripts/ops/claim.sh`'s identity check (#203), which the seat never triggers because it never claims — it never implements, never claims and never reviews its own commits (V0); and the 2026-09-07 double seat was a coordination failure (a handoff file naming a session that had ended), which an identity would not have prevented and a named session in the record does address. Consequences, all durable: the seat never holds or posts under a persona App token and never signs `### Argus` or `### Atlas`; its writes — verdict comments and, while D16 stands, the merge — go under the operator's own credential, whose login is never any persona's `authority.identity`; GitHub's own comment-author and `merged_by` records are the mechanical record of *which login*, and `REVIEW.md`'s signature section gains one bullet for *which session*: a seat comment opens `### Verifier` and its trailer reads `— Verifier · <login> · session <name>`, where `<name>` is the session name the harness exposes to peers (the same value `CLAIM_SESSION` carries). A comment lacking the trailer is not a seat verdict and carries no merge authority (PLAYBOOK's existing rule that a bare-login comment is not an operator decision). Answers Open question 4. |
| D16 | **The seat's interim powers live in `docs/PLAYBOOK.md`, once, under one subsection whose title carries the expiry.** Subsection title: `### Interim: the verifier seat merges on AGREE (retires with #64/#151)`. It holds exactly the three powers that are not review: merge-on-AGREE (merge with branch deletion, verify the commit reached `main` and — repair regime only — that the issue closed by this pull request's own keyword, never by a stray trailer), fix-prompt authoring (a self-contained file in the run archive's `fix-rounds/` directory, path handed to the operator, a fresh implementer session on the same branch), and the observations log (the wave file, written as events happen, with the disposition footnote at close-out), plus the seat's judgment boundaries (scope and product calls surfaced to the operator with a recommendation and decided only after no objection, stated in the record; three no-progress BLOCK rounds are grounds to recommend closing unmerged when a superset exists, with file-level evidence). The passage this replaces already exists and is explicitly provisional: PLAYBOOK's `### Verification` subsection describes the seat today as a "written charter" held in a gitignored run archive. It is rewritten in place — steps 1–7 become a one-line pointer to `REVIEW.md`'s section, former steps 8–9 move into the interim subsection — never appended to, so the file carries one account of the seat. The "Resuming" item that names a home-directory charter is rewritten to say the seat is launched with the compiled review-stage brief under the one launch convention #199 D15 records (this spec names no harness and no brief path — the path follows the pin). The operator's local charter file is thereby retired; its disposal is the operator's. `REVIEW.md` takes only what outlives the exercise (D2, D15, D17) and says nothing about merge-on-AGREE. Answers Open question 1. |

## Acceptance
