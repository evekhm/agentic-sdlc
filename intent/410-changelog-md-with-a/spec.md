# Spec: CHANGELOG.md with Hard CI Merge Gate, Full-History Bootstrap, and Process Update

**Issue:** #410 · **Status:** Approved (approval = merge of this PR) ·
**Author:** athena (`evekhm-athena-app[bot]`) ·
**Open questions:** none

## What is being built

This specification formalizes the introduction of `CHANGELOG.md` at the repository root, accompanied by a fail-closed continuous integration gate (`scripts/ci/changelog_check.sh` running in `.github/workflows/ci-gates.yml`), governance updates across repository standards (`AGENTS.md`, `REVIEW.md`, `personas/odyssey.yaml`), a curated historical backfill covering substantive changes since repository inception, and an audit of `README.md` to eliminate factual drift.

Historically, this repository maintained two living documents that appeared to track progress but served fundamentally different purposes:
1. `docs/SPEC.md` is a living specification structured around permanent capability IDs and written in the present tense to describe what the system does today. It does not provide a chronological narrative of when features landed or why changes were made.
2. `docs/CRITICAL_PATH.md` is an operational tracking log maintained by the advisor seat to monitor in-flight progress toward the autonomous loop milestone. It is not gated by CI, not curated for general human readership, and not designed as a permanent historical log of shipped functionality.
3. `README.md` is specified (#35) to describe the target architecture and design vision; it explicitly excludes release chronology and build status.

Consequently, neither human operators nor automated actors have an accessible, plain-English chronological trail of what was built and why. Substantial behaviors (such as PR #406) have merged into `main` without human-readable summaries anywhere in the repository.

This specification resolves this gap across twelve binding decisions (D1 through D12):

1. **CHANGELOG Placement, Header, and Sectioning (D1):** `CHANGELOG.md` lives at repository root, organized reverse-chronologically by date under `## YYYY-MM-DD` section headers.
2. **Entry Structure, Attribution, and Content Rules (D2):** Each entry occupies an H3 subsection citing the pull request and issue number (`### [PR #<n>](...): <Title> ([#<issue>](...))`), followed by 1 to 3 concise sentences explaining what changed, why, and the operational/user impact. Diff dumps and commit hashes are forbidden.
3. **Dedicated Standalone CI Gate Script (D3):** `scripts/ci/changelog_check.sh` is implemented as an independent, fail-closed check mirroring the CLI and environment interface of `scripts/ci/spec_check.sh`.
4. **Behavior-Bearing Path Parity (D4):** The path obligation matches `spec_check.sh` exactly (`.github/workflows/*`, `scripts/*`, `personas/*`, `config/*`, `AGENTS.md`, `REVIEW.md`), excluding compiled agent targets, intermediate intent artifacts, and operator run logs.
5. **Machine Bypass Marker Syntax and Parsing (D5):** Pull requests touching behavior-bearing paths without user-facing impact must declare `Changelog: none — <reason>` (or `Changelog-impact: none — <reason>`) with a mandatory, non-empty reason.
6. **Parallel GitHub Actions CI Job (D6):** A dedicated `changelog-check` job runs in `.github/workflows/ci-gates.yml` on pull request events (`opened`, `synchronize`, `reopened`, `edited`), allowing body edits to re-evaluate the check without empty commits.
7. **Autonomous Merge Gate and Branch Protection Enforcement (D7):** `scripts/ci/merge_gate.sh` requires no code modifications; conjunct 2 already evaluates the status check roll-up, and `changelog-check` is added as a required status check on `main`.
8. **Process Standards and Persona Governance Updates (D8):** Adds "The changelog (CHANGELOG.md)" to `AGENTS.md`, adds changelog verification to `REVIEW.md`'s implementer checklist, and updates `personas/odyssey.yaml` to require the changelog entry on implementation PRs.
9. **Curated Full-History Bootstrap Backfill (D9):** Odyssey backfills `CHANGELOG.md` with substantive historical PRs from project inception to #410, filtering out noise, typo fixes, and mechanical churn.
10. **`README.md` Fact Audit and Gate Count Sync (D10):** Updates `README.md` to reflect five parallel CI gates and repairs drifted facts identified during the audit.
11. **Hermetic CI Contract Test Suite (D11):** Standalone test suite `scripts/ci/tests/changelog_check_test.sh` exercises all eight contractual scenarios hermetically.
12. **Living Spec Upsert and Scope Boundaries (D12):** Updates `docs/SPEC.md` under `ci.gates` and adds `process.changelog`; bounds implementation changes strictly to the specified files.

```text
CHANGELOG.md                         # new reverse-chronological change log and curated history backfill
scripts/ci/changelog_check.sh        # standalone fail-closed changelog CI verification gate
scripts/ci/tests/changelog_check_test.sh # hermetic contract test suite for changelog gate
.github/workflows/ci-gates.yml       # wires changelog-check as a fifth parallel CI gate
AGENTS.md                            # adds "The changelog (CHANGELOG.md)" standard section
REVIEW.md                            # updates review checklist for changelog verification
README.md                            # audits facts and updates CI gate count from four to five
personas/odyssey.yaml                # adds CHANGELOG.md obligation to implementer persona role
docs/SPEC.md                         # living spec update under ci.gates and process.changelog
intent/410-changelog-md-with-a/spec.md # this specification
```

Files `scripts/ci/merge_gate.sh`, `scripts/ci/review_recorder.sh`, `scripts/ops/work.sh`, and `personas/lifecycle.json` are **not** touched.

## Decisions

| ID | Decision | Rationale |
|---|---|---|
| D1 | **`CHANGELOG.md` Placement, Header, and Sectioning.** `CHANGELOG.md` is located at the repository root. The file opens with a canonical H1 title `# Changelog` and an explanatory header stating that all notable behavioral and user-facing changes are documented in this file. Entries are ordered strictly reverse-chronologically by date under H2 date headings formatted as `## YYYY-MM-DD`. If multiple pull requests merge on the same calendar day, all entries for that day are grouped beneath a single `## YYYY-MM-DD` heading. When adding an entry, if a heading for the entry's date already exists at the top of the file, the new entry is prepended within that date section; if no heading for that date exists, a new `## YYYY-MM-DD` heading is prepended immediately below the preamble. | Establishes a predictable, standardized reverse-chronological structure for changelog entries. Grouping by date avoids redundant date headers when multiple PRs land on the same day. |
| D2 | **Entry Structure, Attribution, and Content Rules.** Each entry within a date section occupies an H3 heading referencing the pull request and issue: `### [PR #<n>](https://github.com/evekhm/agentic-sdlc/pull/<n>): <Descriptive Title> ([#<issue>](https://github.com/evekhm/agentic-sdlc/issues/<issue>))` (unlinked plain text `### PR #<n>: <Descriptive Title> (#<issue>)` is permitted as an acceptable fallback). The body of each entry consists of exactly one to three concise, declarative sentences explaining: (1) what capability or behavior changed, (2) why the change was made (the motivating problem or requirement), and (3) the operational or user-visible impact on operators, personas, or workflows. Entries must not include raw commit SHAs, file lists, diff snippets, or author vanity attributions. | Keeps entries high-signal, readable, and focused on intent and impact. Raw commit details belong in git history; the changelog provides curated context for human readers. |
| D3 | **Dedicated Standalone CI Gate Script (`scripts/ci/changelog_check.sh`).** The changelog gate is implemented as a dedicated executable bash script at `scripts/ci/changelog_check.sh`, rather than modifying or overloading `scripts/ci/spec_check.sh`. The script implements the identical dual-mode invocation contract as `spec_check.sh`: (1) Local usage via `scripts/ci/changelog_check.sh <base-ref> [body-file]`, where `<base-ref>` resolves to a merge base with `HEAD` and an omitted body file defaults to an empty file; and (2) CI usage via required environment variables `BASE_SHA`, `HEAD_SHA`, and `PR_BODY_FILE`. The script operates fail-closed: missing environment variables, unreadable files, or a failing `git diff` exit 1 immediately. An exit code of 0 indicates the obligation is satisfied or not incurred. | Separation of concerns: keeping `changelog_check.sh` distinct from `spec_check.sh` produces unambiguous diagnostic messages, isolates failures, and allows independent local execution and maintenance. |
| D4 | **Behavior-Bearing Path Parity.** `scripts/ci/changelog_check.sh` evaluates changed files between `BASE_SHA` and `HEAD_SHA` against the exact set of behavior-bearing paths defined in `scripts/ci/spec_check.sh`: `.github/workflows/*`, `scripts/*`, `personas/*`, `config/*`, `AGENTS.md`, and `REVIEW.md`. Compiled targets (`.claude/agents/*`, `.agents/*`), intermediate lifecycle artifacts (`intent/**`), test runs (`runs/**`), operator state (`ops/**`), and documentation files (`docs/**`, `README.md`) are excluded. If a diff touches zero behavior-bearing files, the script exits 0 with notice (`no behavior-bearing paths changed; no changelog obligation`). If `CHANGELOG.md` is present in the diff, the obligation is satisfied and the script exits 0 with notice (`CHANGELOG.md is updated in this PR; reviewers verify its entry against the diff`). | Ensures strict parity with existing living-spec enforcement. Intermediate artifacts and operator scratch files do not represent released behavioral changes. |
| D5 | **Machine Bypass Marker Syntax and Parsing Discipline.** If a pull request modifies behavior-bearing paths without introducing user-facing or behavioral changes (such as test-only changes, refactorings, comment corrections, or formatting sweeps), the obligation may be satisfied by including a machine-readable bypass marker in the pull request body. The canonical marker is `Changelog: none — <reason>`. The parser also accepts `Changelog-impact: none — <reason>` as a valid symmetrical alias. Matching is case-insensitive on keyword prefix using pure bash string regex: `^[[:space:]]*[Cc]hangelog(-[Ii]mpact)?:[[:space:]]*[Nn]one(.*)$`. A non-empty reason is strictly required following the separator (em dash `—`, hyphen `-`, colon `:`, or matching parentheses). If a marker is detected without a non-empty reason (e.g. `Changelog: none`), or if "none" is merely part of a larger word (such as "nonetheless"), the check fails with exit code 1. | Provides an explicit, grep-matched escape hatch for non-behavioral PRs while preventing accidental or unreasoned bypasses. Pure bash parsing eliminates grep return-code ambiguities. |
| D6 | **Parallel GitHub Actions CI Job (`changelog-check`).** In `.github/workflows/ci-gates.yml`, a new job named `changelog-check` (`changelog-check — CHANGELOG.md obligation`) is defined alongside `spec-check`, `drift`, `sanitize`, and `execution`. The job runs only on pull requests (`if: github.event_name == 'pull_request'`) with trigger types `[opened, synchronize, reopened, edited]`. Including `edited` ensures that adding or correcting the bypass marker in a pull request body triggers immediate re-evaluation without requiring an empty git commit. The job runs in parallel with other gate jobs and executes `bash scripts/ci/changelog_check.sh` after materializing the PR body into a temporary file. | Parallel execution provides rapid feedback without increasing serial CI latency. Triggering on `edited` avoids friction when authors add missing markers. |
| D7 | **Autonomous Merge Gate and Branch Protection Enforcement.** `scripts/ci/merge_gate.sh` is not modified. In `scripts/ci/merge_gate.sh`, Conjunct 2 (`mergeStateStatus` and check suite evaluation) automatically aggregates all check runs in the pull request's check suite. When `changelog-check` fails, Conjunct 2 evaluates to `false` (logging `mergeStateStatus BLOCKED` or `failing: changelog-check=FAILURE`), autonomously preventing merge. Repository administrators add `changelog-check` as a required status check in GitHub branch protection for `main`. No 12th conjunct is added to `merge_gate.sh`. | Preserves the eleven-conjunct contract of #64. Utilizing Conjunct 2 avoids state machine churn, protects the loop ledger schema, and ensures fail-closed enforcement. |
| D8 | **Process Standards and Persona Governance Updates.** (1) `AGENTS.md` is updated to add a new section titled "The changelog (CHANGELOG.md)" immediately after "The living spec (docs/SPEC.md)". It establishes the mandatory update rule for behavior-bearing PRs, the entry formatting standards, and the bypass marker rules. (2) `REVIEW.md` is updated under "The verification protocol" (implement checklist) requiring reviewers (`argus`, `atlas`) to verify that `CHANGELOG.md` entries are factually accurate, concise, and aligned with the diff, and that bypass reasons on marker lines are valid. Low-quality or inaccurate entries are flagged as `normal` defects. (3) `personas/odyssey.yaml` is updated to include the `CHANGELOG.md` update (or bypass marker) as the fourth required delivery artifact on implementation pull requests (alongside the diff, plan sync, and `docs/SPEC.md` upsert). | Enforces changelog discipline across all agents and human contributors by embedding obligations directly into shared standards and reviewer protocols. |
| D9 | **Curated Full-History Bootstrap Backfill.** During the implementation stage of issue #410, Odyssey performs a one-time curated historical backfill of `CHANGELOG.md` spanning from repository inception (PR #1) to PR #414. Inclusion is restricted to substantive deliverables: new features, compiler and workflow additions, security and credential model upgrades, harness statusline tooling, and significant behavioral bug fixes. Pure maintenance churn (typo fixes, cosmetic reformatting, intermediate review-round repairs, and superseded experiments) is excluded. Entries are organized reverse-chronologically by merge date following the format defined in D1 and D2. | Seeds `CHANGELOG.md` with complete historical context from day one, transforming it into an immediately valuable operational and audit reference. |
| D10 | **`README.md` Fact Audit and Gate Count Sync.** During the implementation stage of issue #410, Odyssey audits `README.md` against `docs/SPEC.md` and codebase reality. `README.md` line 153 is updated to state that **five** CI gates run on every pull request: drift, sanitize, execution, spec-check, and changelog-check. Any other drifted facts regarding persona roles, harness tooling, or dispatch mechanisms identified during the backfill audit are repaired to align with `docs/SPEC.md`. | Restores truthfulness to `README.md` without rewriting its architectural vision or violating #35 standards. |
| D11 | **Hermetic CI Contract Test Suite (`scripts/ci/tests/changelog_check_test.sh`).** A standalone, hermetic test suite is implemented at `scripts/ci/tests/changelog_check_test.sh` to verify all behavior contracts locally and in CI. The suite tests eight discrete scenarios: (1) non-behavior-bearing path changes exit 0; (2) behavior-bearing changes with `CHANGELOG.md` updated exit 0; (3) behavior-bearing changes missing `CHANGELOG.md` and missing marker exit 1; (4) valid `Changelog: none — <reason>` exits 0; (5) valid `Changelog-impact: none — <reason>` exits 0; (6) marker missing reason exits 1; (7) marker prefix false matches (e.g. `Changelog: nonetheless`) exit 1; and (8) positional CLI arguments function identically to CI environment variables. The test suite is wired into `.github/workflows/ci-gates.yml`. | Guarantees regression-free behavior and verifiable compliance across all edge cases without requiring network access or external APIs. |
| D12 | **Living Spec Upsert and Implementation Boundaries.** Implementation changes for issue #410 are strictly confined to: `CHANGELOG.md`, `scripts/ci/changelog_check.sh`, `scripts/ci/tests/changelog_check_test.sh`, `.github/workflows/ci-gates.yml`, `AGENTS.md`, `REVIEW.md`, `README.md`, `personas/odyssey.yaml` (and compiled targets), and `docs/SPEC.md` (upserting capabilities `ci.gates` and `process.changelog`). Files `scripts/ci/merge_gate.sh`, `scripts/ci/review_recorder.sh`, `scripts/ops/work.sh`, and `personas/lifecycle.json` are **not** modified. Per standard repository discipline, the `docs/SPEC.md` living spec upsert is committed in the implementation pull request. | Confines the blast radius to the declared changelog mechanisms, preventing regressions in merge gating or persona lifecycles. |

## Acceptance

- **AT-1 (D1, D2, D9):** `CHANGELOG.md` exists at repository root, opens with `# Changelog`, groups entries under `## YYYY-MM-DD` headings in reverse-chronological order, and contains curated entries from PR #1 through PR #414 where each entry has an H3 header referencing the PR and issue followed by 1 to 3 concise sentences describing what changed, why, and the impact.
- **AT-2 (D3, D4):** Running `scripts/ci/changelog_check.sh` on a diff touching only non-behavior-bearing paths (e.g. `docs/SPEC.md` or `intent/410-changelog-md-with-a/spec.md`) exits with code 0 and outputs `::notice::changelog check: no behavior-bearing paths changed; no changelog obligation`.
- **AT-3 (D3, D4):** Running `scripts/ci/changelog_check.sh` on a diff touching behavior-bearing paths (`scripts/ci/changelog_check.sh`) where `CHANGELOG.md` is also touched in the diff exits with code 0 and outputs `::notice::changelog check: CHANGELOG.md is updated in this PR; reviewers verify its entry against the diff`.
- **AT-4 (D3, D4, D5):** Running `scripts/ci/changelog_check.sh` on a diff touching behavior-bearing paths where `CHANGELOG.md` is not touched and the PR body is empty exits with code 1 and outputs `::error::changelog_check: this PR changes behavior-bearing paths but neither updates CHANGELOG.md nor declares no changelog impact`.
- **AT-5 (D3, D5):** Running `scripts/ci/changelog_check.sh` on a diff touching behavior-bearing paths where `CHANGELOG.md` is not touched but the PR body contains `Changelog: none — pure refactor without behavioral change` exits with code 0 and outputs `::notice::changelog check: declared no changelog impact — pure refactor without behavioral change`.
- **AT-6 (D3, D5):** Running `scripts/ci/changelog_check.sh` on a diff touching behavior-bearing paths where `CHANGELOG.md` is not touched but the PR body contains `Changelog-impact: none — internal test additions only` exits with code 0 and outputs `::notice::changelog check: declared no changelog impact — internal test additions only`.
- **AT-7 (D3, D5):** Running `scripts/ci/changelog_check.sh` on a diff touching behavior-bearing paths where `CHANGELOG.md` is not touched and the PR body contains `Changelog: none` (without a reason) exits with code 1 and outputs `::error::changelog_check: the Changelog marker needs a reason: write 'Changelog: none — <why this diff does not change user-facing or system behavior>'`.
- **AT-8 (D3, D5):** Running `scripts/ci/changelog_check.sh` on a diff touching behavior-bearing paths where the PR body contains `Changelog: nonetheless we proceed` exits with code 1.
- **AT-9 (D6, D7):** In `.github/workflows/ci-gates.yml`, the `changelog-check` job is defined with trigger types `[opened, synchronize, reopened, edited]`, invokes `bash scripts/ci/changelog_check.sh`, and reports status independently alongside `spec-check`.
- **AT-10 (D8):** In `AGENTS.md`, the section "The changelog (CHANGELOG.md)" is present following "The living spec (docs/SPEC.md)"; in `REVIEW.md`, changelog accuracy verification is included in the implementer checklist; and in `personas/odyssey.yaml`, the role description enumerates the `CHANGELOG.md` entry as a required delivery artifact.
- **AT-11 (D10):** In `README.md`, line 153 explicitly references five CI gates (`drift`, `sanitize`, `execution`, `spec-check`, and `changelog-check`).
- **AT-12 (D11):** Executing `bash scripts/ci/tests/changelog_check_test.sh` runs all eight contractual scenarios hermetically and exits with code 0.

## Concerns

- **Merge conflicts on date headers:** When multiple pull requests land on the same calendar day, concurrent branches may attempt to create or edit the same `## YYYY-MM-DD` section. D1 mitigates this by specifying that entries prepend cleanly within the date section, and git's standard 3-way merge cleanly handles distinct subsections under `CHANGELOG.md`.
- **Bypass marker abuse:** Implementers might attempt to bypass the changelog requirement by routinely adding `Changelog: none — internal fix`. D8 mitigates this by instructing reviewers (`argus`, `atlas`) to audit bypass reasons and flag invalid or frivolous bypasses as `normal` defects.
- **Independence of living spec and changelog:** Authors must not assume that updating `CHANGELOG.md` satisfies the living-spec obligation, or vice-versa. `spec-check` and `changelog-check` run as separate, independent gates with distinct error diagnostics and remediation instructions.

## Out of scope

- Automated semver tagging, git release drafting, or package publishing tooling.
- Replacing or modifying `docs/SPEC.md` or `docs/CRITICAL_PATH.md`.
- Rewriting historical git commits or altering commit messages.
- Modifying `scripts/ci/merge_gate.sh` conjunct logic.
