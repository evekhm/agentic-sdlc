# Intent: trusted-posting rule 1 names the posting script

**Issue:** #98 · **Author:** athena (`evekhm-athena-app[bot]`) ·
**Status:** accepted on merge of this PR

## Problem

`personas/skills/trusted-posting.md` rule 1 requires every
workflow-driven GitHub write to go "through the repository's posting
scripts / workflow steps, never ad-hoc API calls composed inline", and
then names no script. When the skill was written there was none to
name. `scripts/ops/post.sh` now exists on `main` (#25, PR #97), but
D10 of that spec forbade the implementing PR from touching
`personas/**`, so the skill still points at nothing.

All six personas declare this skill — argus, atlas, athena, cassandra,
daedalus, odyssey — so all six compile with an instruction whose object
is missing. An instruction of the form "use the sanctioned tool" that
does not say which tool is the shape that gets read, agreed with, and
then improvised around: the persona reaches for a plain API call,
which is precisely what rule 1 forbids. The gap is not theoretical for
this repository, because `post.sh` carries two behaviours a caller
cannot infer and will get wrong on first contact:

- there is deliberately no `--body` flag, so a persona that composes a
  comment as an argument fails and concludes the script is unusable;
- a post suppressed by `hold` exits 0 with one line saying so, so a
  persona that reads "nothing posted" as a failure retries, and
  retrying past a circuit breaker is the exact behaviour `hold` exists
  to stop (#25 D13/D14).

## Proposed outcome

Rule 1 of the skill names the script, its exact invocation, and those
two inherited properties, in the skill's own voice — short enough that
it does not become a second copy of the script's own documentation.
Concretely the rule should leave a cold persona able to answer, from
the compiled prompt alone and without opening `scripts/ops/post.sh`:
what command posts a comment, where the body comes from, and what an
exit-0-with-nothing-posted means.

Every compiled target that declares the skill carries the new text,
regenerated by `python3 scripts/sync_agents.py` and committed, with the
drift gate proving the text reached all of them.

## Affected users and systems

- `personas/skills/trusted-posting.md` — the one hand-edited file.
- The six persona sources that declare the skill, via their compiled
  targets under `.claude/agents/` and `.agents/agents/` — regenerated
  output only, never hand-edited.
- The CI drift gate, which is the proof of delivery for this change.
- No runtime behaviour: `scripts/ops/post.sh` and its tests
  (`scripts/ops/tests/post_test.sh`) landed in PR #97 and are not
  touched here.

## Constraints

- **Unblocked.** PR #97 merged on 2026-09-04, so the script this
  intent names exists on `main`. Nothing else gates the work.
- Skill text plus regenerated compiler output, nothing else. A PR
  under this intent that edits a script, a test or a workflow has
  exceeded its scope.
- Skills are harness-agnostic. The wording must not assume the tool
  surface, flags or transcript conventions of any one harness.
- No second copy: the rule cites the script and the decisions it
  implements (#25 D13/D14); it does not restate the script's exit-code
  table or its hold-set resolution.
- The other four rules of the skill — tokens by name, declared
  authority, graceful degradation, `hold` absolute — keep their
  current meaning; this is an amendment to rule 1, not a rewrite of
  the skill.
- Sanitizer applies as everywhere: no home paths, no credential
  shapes, and a credential is named, never valued.

## Open questions

Two, both scope boundaries rather than blockers. Each is to be closed
as a numbered Decision at the design stage; neither prevents accepting
this intent, and either can be overruled by editing this file at the
merge gate.

1. **How wide is rule 1?** `post.sh` posts *comments*. Applying a
   label, pushing a branch and opening a pull request are also
   workflow-driven writes under the rule's own first sentence, and
   today every persona performs them with plain `gh`/`git`. Either the
   rule is about the comment path and says so, or it claims all writes
   and each persona is presently in violation of it several times per
   issue. The design stage picks one and the wording follows.
2. **Does rule 4's ladder survive?** "Degrade gracefully — full review
   → comment with inline detail → summary comment → issue comment"
   describes a caller choosing among API calls. Once one script owns
   the write, the rungs a persona can still take are the script's own
   outcomes. Whether rule 4 is restated in those terms, or left alone
   as an authoring-level instruction about *what* to post rather than
   *how*, is a design-stage decision.
