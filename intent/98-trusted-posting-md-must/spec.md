# Spec: trusted-posting rule 1 names the posting script

**Issue:** #98 · **Status:** Approved (approval = merge of this PR) ·
**Author:** athena (`evekhm-athena-app[bot]`) ·
**Open questions:** none

## What is being built

Rule 1 of `personas/skills/trusted-posting.md` is updated to name
`scripts/ops/post.sh`, specify its exact invocation, mandate body
delivery via file, and document the exit-0 contract for hold suppression.
The compiled persona targets declaring the skill are regenerated via
`python3 scripts/sync_agents.py` and committed.

```text
personas/skills/trusted-posting.md   # rule 1 updated with post.sh invocation and hold contract
.claude/agents/*.md                  # regenerated compiled targets declaring the skill
.agents/agents/*/agent.md            # regenerated compiled targets declaring the skill
```

No code, no runtime scripts, no test files, no workflows, and no
`docs/SPEC.md` entries are touched.

## Decisions

| ID | Decision | Rationale |
|----|----------|-----------|
| D1 | **Rule 1 scope: comment posting on issues and pull requests (closes OQ1).** Rule 1 explicitly governs the comment posting path on GitHub issues and pull requests via `scripts/ops/post.sh`. Other git and GitHub operations performed across persona lifecycles — pushing topic branches via `git`, opening pull requests via `gh pr create`, or label updates managed by scripts or workflows — are governed by each persona's declared `authority` block (rule 3) and standard repository workflows, not by `post.sh`. | Resolves Open Question 1. `scripts/ops/post.sh` is designed to post comments on issues and pull requests (`gh api -X POST repos/<repo>/issues/<number>/comments`). If rule 1 purported to govern all GitHub writes including git pushes and pull request creation, every persona would be in constant violation. Explicitly scoping rule 1 to comments aligns the rule with what `post.sh` actually implements and validates. |
| D2 | **Rule 4 degradation ladder semantics (closes OQ2).** Rule 4 ("Degrade gracefully") survives unchanged as an authoring-level instruction governing payload compression and reporting granularity (e.g. falling back from full inline detail to a summary comment), not an instruction to bypass `post.sh` or attempt ad-hoc API fallbacks. Rule 4's text is not modified. For execution failures, a `post.sh` exit 1 is a hard failure (unusable input, attribution mismatch, or API failure) to report and halt on without switching identities, while exit 0 (including hold suppression) is successful termination. | Resolves Open Question 2. In unattended execution, `post.sh` is the sole posting path, so a caller cannot fall back to alternate API calls when an API write fails. However, the authoring concept of condensing output when encountering size limits or formatting constraints remains a valid model discipline. Clarifying this as authoring-level keeps rule 4 intact without conflicting with rule 1 or reopening skill rewrite scope. |
| D3 | **Exact text and contract of Rule 1.** Rule 1 in `personas/skills/trusted-posting.md` is replaced with the following exact text:<br><br>"1. **Vetted steps only.** All comment posting on issues and pull requests goes through `scripts/ops/post.sh <number> --as <persona> --body-file <path>`, never ad-hoc API calls composed inline. The body is always a file (there is deliberately no `--body` flag). `hold` is re-read immediately before the write across the target and any closed issues (#25 D13/D14); a hold-suppressed post exits 0 with a notice and must not be retried. The script owns authentication, attribution verification, and escaping." | Fulfills the primary requirement of #98. It names `scripts/ops/post.sh`, provides the exact parameter syntax, explicitly specifies that the body is provided via `--body-file` and that `--body` does not exist (preventing common command composition failures), and explains the exit 0 behavior on `hold` suppression so models do not interpret suppression as an error to retry. It cites #25 D13/D14 rather than duplicating the implementation details of the hold set or exit codes, maintaining a single source of truth. |
| D4 | **Scope boundary and compiler synchronization.** The implementing change touches ONLY `personas/skills/trusted-posting.md` and the compiled targets under `.claude/agents/` and `.agents/agents/` regenerated by `python3 scripts/sync_agents.py`. No scripts (`scripts/**`), test files (`tests/**`), workflows (`.github/workflows/**`), configuration (`config/**`), or living spec (`docs/SPEC.md`) may be modified. Compiled targets must never be hand-edited; the CI drift gate (`python3 scripts/sync_agents.py --check`) is the proof of clean compilation and delivery. | Keeps the change strictly within the boundaries established by the accepted intent. `scripts/ops/post.sh` is already implemented and tested on `main` (PR #97), and its behavior is already reflected in `docs/SPEC.md:853-867`. Therefore, no runtime or living-spec changes are warranted or permitted. |
