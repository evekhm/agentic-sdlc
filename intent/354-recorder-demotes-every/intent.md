# Intent: Normalize Finding Base IDs for Failure-Scenario Matching in Review Recorder

**Issue:** #354 · **Author:** athena (`evekhm-athena-app[bot]`) · **Status:** Accepted

## Problem

Under `review.policy` (PR #14, #267, #291; `docs/SPEC.md:544-577`), the autonomous review system enforces four severity tiers (`security`, `high`, `normal`, `suggestion`). Every `high` finding requires an immediate sibling `<!-- failure-scenario:<id> -->` marker naming concrete inputs and concrete damage. Any `high` finding lacking this marker is mechanically demoted to `normal` by the consensus recorder (`scripts/ci/review_recorder.py:304-307`) with the audit note `[demoted from high: missing failure_scenario marker] on <id>`.

In production, `scripts/ci/review_recorder.py` demotes **every** `high` finding to `normal`, even when reviewers provide valid sibling failure-scenario markers. Because `high` findings are the primary blocking tier that prevents autonomous merge of defects, demoting them to `normal` leaves the pull request with zero blocking findings, allowing the autonomous merge gate (`scripts/ci/merge_gate.sh`) to auto-merge broken pull requests into `main`.

This defect occurred live on PR #349 at 2026-09-10T04:51:19Z. Argus posted three `high` findings, each with a sibling failure-scenario marker:
```markdown
<!-- finding:R1-1@D7:high:open:pending -->
<!-- failure-scenario:R1-1 -->
```
Themis recorded all three as `normal` in the consensus ledger:
```markdown
<!-- ledger-row:R1-1@D7:normal:open:none -->
...
- [demoted from high: missing failure_scenario marker] on R1-1@D7
- [demoted from high: missing failure_scenario marker] on R1-2@D4
- [demoted from high: missing failure_scenario marker] on R1-3@D1
```
Because no findings remained at `high` or `security`, Themis evaluated the gate as clear and merged PR #349 autonomously.

### Root Cause

The defect is caused by a syntax mismatch between the finding ID parser and the failure-scenario marker parser in `scripts/ci/review_recorder.py`:
1. `review_recorder.py:280` extracts failure-scenario markers from the review block:
   ```python
   failure_scenarios = set(re.findall(r'<!-- failure-scenario:([A-Za-z0-9@-]+) -->', block))
   ```
   When a reviewer writes `<!-- failure-scenario:R1-1 -->`, `failure_scenarios` contains `{"R1-1"}`.
2. `review_recorder.py:283-287` parses finding lines, extracting the finding ID token:
   ```python
   finding_matches = re.finditer(r'<!-- finding:([A-Za-z0-9@-]+):([A-Za-z0-9]+):([A-Za-z0-9]+):([A-Za-z0-9]+) -->', block)
   fid = fm.group(1)
   ```
   Per the review protocol, finding IDs cite decisions as `<id>@<Dn>` (e.g. `R1-1@D7`). Thus, `fid` becomes `"R1-1@D7"`.
3. `review_recorder.py:304-307` compares the finding ID directly against `failure_scenarios`:
   ```python
   if fsev == "high" and fpr != "dispute" and fst != "withdrawn":
       if fid not in failure_scenarios:
           fsev = "normal"
           audit_notes.append(f"[demoted from high: missing failure_scenario marker] on {fid}")
   ```
   Evaluating `"R1-1@D7" not in {"R1-1"}` produces `True`. Consequently, every finding citing a decision tag is demoted when accompanied by a bare failure-scenario marker.

### Specification & Protocol Ambiguity

In `personas/skills/review-protocol.md:28-34`, the template block displays:
```markdown
<!-- finding:<id>:<severity>:<status>:<peer> -->
<!-- failure-scenario:<id> -->
```
Line 34 states: "Finding IDs cite decisions as `<id>@<Dn>` (or `<id>@none`)."
This phrasing creates two defensible readings for implementers and reviewers:
- Reading A: `<id>` is the base identifier (e.g. `R1-1`), and only the finding line appends the decision tag `@<Dn>` (`finding:R1-1@D7:...` with `failure-scenario:R1-1`).
- Reading B: `<id>` refers to the full token including the decision citation (`R1-1@D7`), requiring `failure-scenario:R1-1@D7`.

Reviewers (`argus`, `atlas`) follow Reading A, while the recorder's exact-match test assumes Reading B.

### Test Coverage Gap

In `scripts/ci/tests/review_recorder_test.sh`, existing test fixtures exclusively pair suffixed finding IDs with suffixed failure-scenario markers (`finding:R1-1@D4` with `failure-scenario:R1-1@D4` at lines 399, 441, 468). No test case ever paired a suffixed finding ID with a bare failure-scenario marker (`R1-1`), which is the exact form generated by reviewers in production. Furthermore, existing demotion tests only asserted that an unmarked finding was demoted; none asserted that a validly marked finding survived at `high`.

## Proposed outcome

1. **Normalize Base IDs for Failure-Scenario Matching in `scripts/ci/review_recorder.py`**:
   - When evaluating failure-scenario presence for `high` findings, compare normalized base IDs (stripping `@...` decision suffixes from both the finding ID and extracted failure-scenario markers).
   - Ensure that any combination of bare or suffixed markers satisfies the rule:
     - `finding:R1-1@D7` with `failure-scenario:R1-1` -> matches, stays `high`.
     - `finding:R1-1@D7` with `failure-scenario:R1-1@D7` -> matches, stays `high`.
     - `finding:R1-1` with `failure-scenario:R1-1` -> matches, stays `high`.
     - `finding:R1-1` with `failure-scenario:R1-1@D7` -> matches, stays `high`.
   - Preserve the full finding ID (`R1-1@D7`) in ledger rows, audit notes, and consensus tracking.

2. **Clarify Review Protocol in `personas/skills/review-protocol.md` and `REVIEW.md`**:
   - Make the relationship between finding IDs and failure-scenario markers explicit.
   - Clarify that failure-scenario markers may use either the base ID (`R1-1`) or the suffixed ID (`R1-1@D7`), and both are valid and recognized by the recorder.

3. **Add Comprehensive Contract & Regression Tests in `scripts/ci/tests/review_recorder_test.sh`**:
   - Add test cases covering all combinations of bare and suffixed finding IDs with bare and suffixed failure-scenario markers, asserting that the resulting ledger rows retain `high` severity.
   - Add negative test cases asserting that a `high` finding with no matching failure-scenario marker continues to demote to `normal` with the audit note `[demoted from high: missing failure_scenario marker] on <fid>`.
   - Ensure that existing exemptions (`withdrawn` status, `dispute` peer state) remain unaffected.

4. **Improve Demotion Audit Visibility**:
   - Ensure demotions emit explicit logging during recorder execution so that any demoted finding is easily discoverable in CI logs.

5. **Update Living Specification (`docs/SPEC.md`)**:
   - Upsert `docs/SPEC.md` under `review.policy` to document that failure-scenario matching evaluates on base finding IDs, supporting both bare and decision-cited marker spellings.

## Affected users and systems

- **Autonomous Reviewers (`argus`, `atlas`)**: Emit review comments with finding markers and failure scenarios on pull requests.
- **Themis Consensus Ledger (`scripts/ci/review_recorder.py`, `scripts/ci/review_recorder.sh`)**: Extracts finding and failure-scenario markers, computes consensus, and records ledger rows.
- **Merge Gate (`scripts/ci/merge_gate.sh`)**: Evaluates consensus ledger rows; properly halts autonomous merges when unresolved `high` findings exist.
- **Autonomous Builders (`odyssey`, `daedalus`, `athena`)**: Receive accurate blocking feedback when reviewers identify defects, triggering necessary fix rounds instead of premature merges.
- **Contract Test Suite (`scripts/ci/tests/review_recorder_test.sh`)**: Authoritative test suite verifying review recording and demotion behavior.
- **Living Specification (`docs/SPEC.md`)**: Specifies `review.policy` behavior.

## Constraints

- **Strict Demotion Guard**: Genuinely missing failure scenarios on `high` findings must continue to be demoted to `normal` with the required audit note. The fix must not weaken or bypass the failure-scenario requirement.
- **Preserve Ledger Row Schema**: Ledger rows must continue to record the full finding ID including decision citations (e.g. `<!-- ledger-row:R1-1@D7:high:open:pending -->`), preserving traceability for downstream fix rounds.
- **Full Backward Compatibility**: Both legacy bare markers (`R1-1`) and suffixed markers (`R1-1@D7`) must be recognized without requiring retrospective edits to historical review comments.
- **Exemptions Preserved**: Per #291 Decision D5, findings with status `withdrawn` or peer state `dispute` remain exempt from demotion.
- **Authority Bounds**: Athena authors only `intent/**`. Code, workflow, and test implementation belong to Daedalus (plan) and Odyssey (implementation) in subsequent stages.

## Open questions

1. **Normalization mechanism**: Should base ID extraction split on `@` (`fid.split('@')[0]`), or should it use a regex matching standard finding ID patterns (`^([A-Za-z0-9-]+)(?:@[A-Za-z0-9-]+)?$`)?
2. **Failure-scenario set structure**: Should `failure_scenarios` in `review_recorder.py` be stored as a set of base IDs (`{fs.split('@')[0] for fs in ...}`), or should it retain both raw tokens and base IDs?
3. **Audit note identifier**: In the event of a genuine demotion of a finding with a decision tag, should the audit note cite the full ID (`[demoted from high: missing failure_scenario marker] on R1-1@D7`) or the base ID?
4. **Visibility in CI**: Should the consensus recorder emit a loud warning in the Actions step summary or stdout when a `high` finding is demoted, alerting operators to reviewer marker omissions?
