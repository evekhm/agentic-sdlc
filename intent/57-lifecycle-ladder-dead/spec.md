| D1 | **The implement rung advances on a merged pull request found in the pushed range, not on a path and not on a branch name read from a merge commit.** For every commit in `git rev-list --first-parent <before>..<after>`, the advancer asks `gh api repos/<repo>/commits/<sha>/pulls` for the pull requests that commit belongs to, and keeps those with a non-null `merged_at` whose `base.ref` is the default branch, de-duplicated by number. Of the intent's three readings, the merge-commit branch name (a) is silent on a squash merge — the merge commit and the branch name both disappear — and an explicit marker (c) is a step an implementer can forget, which re-creates the same silent dead-end this issue exists to kill. The API lookup is the one signal that survives merge-commit, squash and rebase merges identically. `--first-parent` is what main actually gained: the commits on a merge's second parent all resolve to the same pull request and would only cost redundant calls. The hotfix pushed straight to an `odyssey/<n>-*` branch with no pull request deliberately does **not** advance — everything reaches `main` by pull request (AGENTS.md, "Working the tracker", step 4), and a push that bypassed review must not open a review rung. **Amended 2026-09-04 (athena, defect #72: Argus F2 and F11).** Two clauses are retracted as factually false in this repository. The rule clause read *"whose `base.ref` is the default branch"*; the rationale clause read *"`--first-parent` is what main actually gained: the commits on a merge's second parent all resolve to the same pull request and would only cost redundant calls."* `c169bb7` is "Merge pull request #45 from evekhm/odyssey/36-35-land"; its second parent contains `85198c3` = "Merge pull request #42" (`odyssey/35-readme` → base **`daedalus/35-readme`**), and `gh api repos/…/commits/c169bb7/pulls` returns only #45. Containment *is* the trunk test the base filter was trying to be: a pull request merged into a branch that never lands has no commit in any range, and one merged into a branch that does land is discovered exactly once, in the range that landed it. It holds identically for merge-commit, squash and rebase merges, which is the property this row was written to buy. The rejected reading — keep `--first-parent`, and make a landing merge a counted failure telling a human to advance the rung by hand — differs on exactly PR #42: it exits 1 and writes nothing where this one advances #35 to `status:in-review` naming #42. It is rejected because a rung a human has to close by hand is the dead end this issue exists to kill (INTENT.md's ladder; D9's rationale, "a silently dead-ended ladder is the whole content of this issue"), and because what made the trunk test wrong was the retracted optimisation, not the design. **Amended 2026-09-04 (athena, round-1 review of #96: Atlas AT-20, Argus R1-8 and R1-10).** Three clauses, none of them a change of shape. **(a) The walk is ordered, not merely reversed (AT-20, and R1-5's resolution in D15).** It is `git rev-list --topo-order --reverse "$BEFORE..$AFTER"`. Without `--topo-order` the base ordering is commit date, which interleaves parallel branches arbitrarily and ties outright on equal timestamps — and once this row stopped walking `--first-parent` the range is a graph, not a line, so "oldest first" and "the later one wins" were both undefined. `--topo-order --reverse` is a total order on the range that contains each commit exactly once, so the position of a pull request's `merge_commit_sha` in that list is a well-defined integer, deterministic for a given DAG and reproducible in a fixture. That integer is what D15's second-candidate rule ranks on. **(b) The fan-out is stated rather than left to the implementer (R1-8).** The number of `gh api --paginate .../commits/<sha>/pulls` calls per push equals the range's commit count; the ceiling is the workflow's `timeout-minutes: 10` (`.github/workflows/lifecycle.yml:46`), and no other cap is imposed. A lookup that fails for any reason, rate limiting included, is already `fail_issue` at `:203-206` — red, counted, never silent — and that is the correct outcome, because a discovery step that could not see part of the range must not report "nothing to advance". The cheaper reachability-bounded walk R1-8 proposes — merge commits plus commits with no parent in the range — is **declined**, with its differing case: a pull request squash- or rebase-merged into a landing branch has no merge commit of its own and a parent that is inside the range, so that walk never asks about it and it produces no candidate, silently. Trading a bounded call count for a rediscovered class of invisible merges is trading away this row's whole subject. If the budget ever binds, the fix is a cap that fails **loudly** on the commits it did not examine, not a walk that quietly skips them. **(c) R1-10, no behaviour change:** the counted failure's reason is softened from *"its only cause is a shallow clone"* to "the checkout does not contain it", and the message names `fetch-depth: 0` as the likely cause rather than the only one. |
