# Spec: close the label ladder's last rung

**Issue:** #57 · **Status:** Approved (approval = merge of this PR) ·
**Author:** athena (`evekhm-athena-app[bot]`) ·
**Open questions:** none

The accepted intent (`intent.md`, merged in 7ef152a) left three Open
questions and named three further collisions the design stage had to
answer either way. No human was live in the design session, so each is
resolved below with its rationale grounded in the code, rather than
posed back. **Any row in this table can be overruled by editing this
file at the merge gate** — the merge is the acceptance, so an edited
row *is* the decision, not a comment asking for one.

Open question 1 lands as D1, D2 and D3; Open question 2 as D8; Open
question 3 as D7. The `Closes #<n>` collision is D9, #52's AT-4 is
D10.

## What is being built

```text
personas/lifecycle.json            + advances_on on all five rows;
                                     the implement row gains a message
scripts/ci/lifecycle_advance.sh    merge-driven transition, intent:new
                                     clearing, null-safe reads, header

scripts/ci/tests/lifecycle_advance_test.sh  new hermetic scenarios
docs/SPEC.md                       lifecycle.labels + personas.resume
AGENTS.md, README.md               one clause each (D9, D8)
```

## Decisions

| ID | Decision | Rationale |
|----|----------|-----------|
| D1 | **The implement rung advances on a merged pull request found in the pushed range, not on a path and not on a branch name read from a merge commit.** For every commit in `git rev-list --first-parent <before>..<after>`, the advancer asks `gh api repos/<repo>/commits/<sha>/pulls` for the pull requests that commit belongs to, and keeps those with a non-null `merged_at` whose `base.ref` is the default branch, de-duplicated by number. Each surviving pull request resolves to at most one candidate issue (D2). A commit that belongs to no pull request yields no candidate. | The rung's output is code, so there is no added path to match (`lifecycle_advance.sh:133`) and the `artifact` column is `null` (`personas/lifecycle.json:48`). Of the intent's three readings, the merge-commit branch name (a) is silent on a squash merge — the merge commit and the branch name both disappear — and an explicit marker (c) is a step an implementer can forget, which re-creates the same silent dead-end this issue exists to kill. The API lookup is the one signal that survives merge-commit, squash and rebase merges identically. `--first-parent` is what main actually gained: the commits on a merge's second parent all resolve to the same pull request and would only cost redundant calls. The hotfix pushed straight to an `odyssey/<n>-*` branch with no pull request deliberately does **not** advance — everything reaches `main` by pull request (AGENTS.md, "Working the tracker", step 4), and a push that bypassed review must not open a review rung. |
| D2 | **A merged pull request resolves to its issue by the head branch first and a closing keyword second; two signals that disagree is a counted failure naming both, never a guess.** `<actor>/<n>-<slug>` on `head.ref` gives `<n>`; otherwise a closing keyword plus a same-repo `#<n>` in the body, in the forms `ops.dispatch` already honours. If both are present and name different issues, the advancer logs `::error::` naming both and the run ends red without writing. | Both signals are the ones `scripts/ops/work.sh` already implements (`ops.dispatch`, #36 D9), so no new convention appears. The **order is deliberately the reverse** of work.sh's, because the two answer different questions: work.sh is handed a pull-request number by an operator and takes the closing keyword as that operator's explicit statement of intent, while the advancer is asking whose ladder this merge advanced — and by D9 the implementing pull request is precisely the one that must **not** carry a closing keyword for the ladder issue. Branch-first is therefore correct in strictly more cases and identical in the compliant one. Never-guess on disagreement is the same rule the multiple-`status:*` check already follows (#4, D1). |
| D3 | **The trigger stays one workflow, one entrypoint, one range; the workflow's only change is `pull-requests: read`.** `.github/workflows/lifecycle.yml` keeps `on: push: branches: [main]` and keeps calling `scripts/ci/lifecycle_advance.sh <before-sha> <after-sha>`. Its `permissions:` block becomes `issues: write, contents: read, pull-requests: read`. No `pull_request` trigger, no second job, no secret, still the default `GITHUB_TOKEN` posting as `github-actions[bot]`. | A `pull_request: closed` trigger would give the pull request for free but would split the advancer's input model in two, and the second half would not be reachable by `scripts/ci/lifecycle_advance.sh <before> <after>` — breaking "runnable locally by the same command CI runs", which is a stated property of `lifecycle.labels` and the reason anyone can debug this script. One read scope is the whole cost, and the intent named the workflow's `issues: write, contents: read` / no-secrets posture as the budget: this stays inside it. |
| D4 | **The ladder file gains one column, `advances_on`, with values `"artifact"`, `"merge"` and `null`.** plan, design and build carry `"artifact"` (fire when the row's `artifact` is ADDED in the range); implement carries `"merge"` (fire when a merged pull request resolves to an issue whose single `status:*` label equals this row's `label`); review carries `null` (no event advances it). The implement row's `artifact` stays `null`. The advancer reads the column; it never infers the trigger. | The intent states the choice is "a new key read by the script, or a second selector — the same decision seen from the data side". Inferring "a null `artifact` means a code merge" would put the trigger rule in the script, which is the fourth copy of the ladder that `personas/lifecycle.json` exists to prevent (#36, D2). An explicit column keeps the trigger in the one table all three readers see, and gives #52's AT-3 validator a field with a closed value set to check. The extra key is inert for the other two readers: `scripts/ops/work.sh` selects on `label` and the compiler renders `stage`/`label`/`artifact`/`advances_to`/`dispatch_brief`, so no compiled target changes and no rebuild is owed. |
| D5 | **A merge candidate joins the existing per-issue contest; it does not get a second guard chain.** Discovery is the only new step. Once an issue is a candidate, it goes through the loop exactly as it does today: read state and labels in one `gh issue view`; skip a non-OPEN issue (D9 narrows this); `hold` first and absolute; more than one `status:*` → comment, apply `hold`, stop. Rank is the row's position in `.stages` plus one — the same formula the artifact path uses — so when one push both adds an artifact and merges a pull request for the same issue, "furthest transition wins, in one comment" applies unchanged. An issue with no `status:*` label, or one whose row's `advances_on` is not `"merge"`, yields no merge candidate. | Every invariant the script documents at lines 30–47 is load-bearing and none of them is about how a candidate was discovered. Duplicating the chain for a second discovery path is how the two halves drift; reusing the existing rank contest means the compression rule is still written once. The `advances_on` gate is also what keeps the two paths disjoint: Athena's own spec pull request merges from `athena/57-…` while #57 sits at `status:spec`, whose row is `"artifact"` — so it advances once, by the added file, and not twice. |
| D6 | **Idempotency needs no new marker: the label gate is the guarantee.** The comment marker keeps its existing shape, `<!-- lifecycle:<advances_to without the "status:" prefix>:<after-sha> -->`, so the implement transition posts `<!-- lifecycle:in-review:<sha> -->`. No other idempotency mechanism is added. | A merge candidate exists only while the issue's current label equals the row's `label` (D4). The moment the transition writes `status:in-review`, the same pull request can never produce a candidate again — in this range, a wider re-run, or any later push. That is a stronger property than the marker gives the artifact path, and it is free. Re-running a range therefore stays a no-op, which is the invariant at line 41 and what makes a manual re-run safe after a partial failure. |
| D7 | **The advancer clears `intent:new` with every `status:*` it writes; `status:planning` gains no writer here.** Whenever the advancer sets a stage label it removes `intent:new` in the same `gh issue edit` if the issue carries it. When the target label is already present and `intent:new` is too, the removal still happens — the "already at target, no label write" short-circuit must not swallow it. A Draft spec, which advances nothing, removes nothing. `status:planning` remains a provisioned label with no automated writer, and `scripts/ops/work.sh`'s "`intent:new` and no `status:*` means the first rung" case stays load-bearing and is **not** edited by this change. | Reading (b) — intake writes `status:planning` at filing — needs an intake writer, which is #10, unbuilt; the intent's "Depends on: nothing open" forbids taking that dependency, and `scripts/ops/work.sh` belongs to #43 this week. Reading (a) extends the one component that already writes labels on every transition, at the cost of one CSV entry and no new trigger, permission or file. It is **reversible**: if #10 later writes `status:planning` at intake, this removal becomes a no-op by presence and work.sh's special case becomes dead code that #10 can delete. The invariant the intent fixed — no item ever carries `intent:new` alongside a `status:*` — holds from the first transition onward under either reading. #57 itself, which carries both today, is repaired by its own next gate. |
| D8 | **The review rung is the last rung: nothing advances past it and nothing closes the issue. Closure is the human's act, and the ladder is silent about it.** `advances_to` and `advances_on` stay `null` on the review row. The advancer never closes an issue, never reopens one, and never writes `review:1..3` or `status:review-stuck`. README's "Review … this rung ends the ladder" gains one clause saying the item is closed by the human when the review is done. | Reading (b) — a terminal transition that closes the issue — requires the advancer to decide that review is *complete*, and completeness is review state: rounds, consensus, the `review:N` counter. That is #8/#9's, and an advancer that also read it would be the two state machines racing over one issue that the script header (lines 25–28) names as the thing it refuses to be. It also collides with authority: the reviewers are comment-only and the human is the sole merge and close authority on every path (README, "What you merge"). So the ladder ends where `personas/lifecycle.json` already says it ends, by construction rather than by a new rule. |
| D9 | **The implementing pull request does not carry `Closes #<n>`; a closed issue sitting at the merge rung is a red failure, not a silent skip.** AGENTS.md's rule is unchanged — a closing keyword belongs on the pull request that completes the issue's *final* stage — and gains one clarifying clause: in the five-rung flow the final rung (review) produces a review, not a pull request, so no pull request in that flow carries `Closes #<n>` and the human closes the issue (D8). The defect-repair path (#32, README) is untouched: its fix pull request *is* the final stage and keeps its closing keyword, and the defect issue was never on the ladder, so no candidate is produced. In the advancer, the non-OPEN skip at line 225 stays a quiet `log` for an artifact candidate, and becomes a `::error::` counted failure — run exits 1, the push shows red — for a merge candidate whose closed issue still carries the row's `label`. Nothing is written to that issue: no label, no comment, no reopen. | The collision is real and silent today: `Closes #57` on the implementing pull request means the push that should write `status:in-review` finds a closed issue and skips it, and the review rung is entered by nobody, forever. Two repairs were available. Making the advancer tolerate a closed issue would have automation labelling issues a human deliberately closed and would hand the script an opinion about closure that D8 just denied it. Keeping the skip and making it *loud* preserves both — "a closed issue has no stage to advance" stays true — while converting the failure mode from an invisible dead-end into a red X on the merge commit, which is the only signal a human reads. Red rather than a warning, because a silently dead-ended ladder is the whole content of this issue. |
| D10 | **#52's AT-4 is repaired here, in the advancer only; AT-3 stays with #52.** `advances_to` and `advance_message` are read with `jq -r '… // empty'` so a JSON `null` is an absent value rather than the four-character string `null`. An empty target writes no label (the existing guard at line 325, now actually reachable); an empty message posts **no comment at all** — a new guard, because today an empty message would post a body with a blank line where the sentence belongs. The Draft override keeps its own message and its own warning comment, unchanged. Validating `personas/lifecycle.json` against `schema.json` in `scripts/sync_agents.py --check` (AT-3) is **not** done here and #52 stays open owning it, with one field added to its job: `advances_on` is `"artifact"`, `"merge"` or `null`, `"artifact"` exactly when `artifact` is non-null, and `null` exactly on the last rung. | AT-4 is latent only because the last rung is unreachable, and this change is what makes it reachable — shipping the two apart would ship a live defect for the length of the gap, which the intent forbids ("may be folded in or sequenced, but not ignored"). It is two `jq` filters and one guard in a file this change already opens. AT-3 is a different file (`scripts/sync_agents.py`), a different failure mode (a bad source compiles green) and a different test surface; folding it in would widen this change into #52's territory for no shared code. |
| D11 | **The comment text is read from the table, and the two sentences that become false are rewritten.** The implement row's `advance_message` becomes: `Implementation merged (IMPLEMENT gate). Next: two independent reviewers read the change and post findings — dispatch each with \`scripts/ops/work.sh <issue> --as argus\` and \`--as atlas\`. This is the last rung: nothing advances past it, and closing the issue is the human's.` The shared `COMMENT_HEADER` (`lifecycle_advance.sh:162-164`) becomes: `_Posted by \`.github/workflows/lifecycle.yml\` (#4) — deterministic, no model call. This workflow writes the \`status:*\` ladder up to and including \`status:in-review\`, and clears \`intent:new\` with the first status it writes. The \`review:1..3\` counter and \`status:review-stuck\` are review state and belong to the review automation (#8/#9)._` The script's own header block (lines 25–28) is reworded to match. The trigger line becomes `Trigger: pull request #<pr> merged in <sha12>.` for a merge candidate and keeps `Trigger: \`<path>\` added in <sha12>.` for an artifact candidate. | The header and the header block both assert today that this workflow writes only `status:planning`→`status:implementing` and that `status:in-review`'s writer arrives with #8/#9. Both become false with D1, and the intent lists retiring them as an outcome. The new wording keeps the same two-part shape — what this workflow writes, and what it deliberately does not — so the boundary with #8/#9 is still stated on every comment. The message itself lives in the table, not the script, per #36 D2; only the header, which is about the workflow rather than about a rung, stays in the script. |
| D12 | **`docs/SPEC.md` is upserted by the implementing pull request: `lifecycle.labels` and `personas.resume`, both in place.** `lifecycle.labels`: the merge-driven transition and how a pull request resolves to an issue (D1, D2); `advances_on` as the trigger column (D4); the `intent:new` clearing (D7); `pull-requests: read` (D3); the closed-issue-at-the-merge-rung red failure (D9); the null-safe reads (D10). Its closing sentence — "`status:in-review` and the `review:N` counter exist in the taxonomy but are not written by this workflow; their writers arrive with #8/#9" — is replaced by the true one: the ladder is written end to end here, and `review:N` / `status:review-stuck` remain #8/#9's. `personas.resume`: the key list gains `advances_on`, and "matches on `artifact` to pick a transition" becomes "matches on `advances_on`, then on `artifact` or on the issue's current `label`". Both cite `(PR #<n>)`. No entry is added and none is deleted. | The living-spec rule: any pull request that changes behaviour upserts `docs/SPEC.md` in the same pull request, rewording superseded entries in place rather than appending (AGENTS.md, "The living spec"). Both entries make claims this change falsifies, and both are the entries a reader consults to learn the ladder. Naming them here means the implementer does not have to rediscover which sentences died. |
| D13 | **The tests are hermetic and pull every expected string out of the ladder file at run time.** `scripts/ci/tests/lifecycle_advance_test.sh` keeps its throwaway repository, its `DRY_RUN=1` and its stub `gh` first on `PATH`; the stub learns exactly one new answer, `api repos/*/commits/<sha>/pulls`, returning a fixture array — so the pull-request lookup goes through `gh` and never through `curl` or the network. Any other `gh` invocation is still recorded as an attempted write and still fails the run. New scenarios assert the merge transition, the branch/keyword resolution and its disagreement failure, the closed-issue red path, the `intent:new` clearing, and the last rung's no-op. Expected labels and messages are read with `jq` from the fixture copy of `personas/lifecycle.json`, never hardcoded. | This is the property the existing suite is built to protect (`lifecycle_advance_test.sh:11-17`): a copy of the ladder hidden in the script must keep failing. A merge path whose expected label was a literal in the test would be exactly that copy, one layer down. Routing the lookup through `gh` rather than `curl` is what keeps the suite offline and what keeps DRY_RUN honest. |

## Acceptance

Each item is observable and cites the Decisions it derives from.

1. `jq -e '[.stages[].advances_on] == ["artifact","artifact","artifact","merge",null]' personas/lifecycle.json` passes, `jq -e '.stages[3].artifact == null and .stages[3].advance_message != null' personas/lifecycle.json` passes, and the file's `_comment` key list names `advances_on` (D4, D11).
2. A hermetic scenario in which the range's first-parent commit belongs to a merged pull request whose head branch is `odyssey/999-test`, with #999 at `status:implementing`, prints `--add-label status:in-review`, `--remove-label` containing the previous status label, the implement row's `advance_message` read from the fixture JSON, and `<!-- lifecycle:in-review:<after-sha> -->` (D1, D4, D6, D11, D13).
3. The same scenario with the pull request's head branch replaced by one that matches no `<actor>/<n>-<slug>` pattern and a body carrying `Closes #999` resolves to #999 and produces the identical transition; with the branch naming #999 and the body carrying `Closes #998`, the run exits 1, names both numbers, and the write log is empty (D2).
4. A squash-style range — one commit on `main`, no merge commit, the stub returning that commit's merged pull request — produces the transition; a range whose commits belong to no pull request produces no merge candidate and exits 0 with the existing "nothing to advance" path intact (D1).
5. With #999 CLOSED and still carrying `status:implementing`, the run exits 1 with an `::error::` naming #999 and the closing-keyword collision, and writes nothing — no label, no comment, no reopen. With #999 CLOSED and carrying no `status:*`, the run exits 0 and logs the existing quiet skip (D9).
6. `hold` on a merge candidate produces no label and no comment; two `status:*` labels on a merge candidate produce the corrupted-state comment and `hold`, byte-identical to the artifact path's; a merge candidate whose issue carries no `status:*` yields nothing. A range that both adds `intent/999-test/plan.md` and merges a pull request for #999 applies one transition and posts one comment (D5).
7. Re-running any range that already advanced an issue writes nothing and exits 0; running the merge scenario twice against an issue already at `status:in-review` produces no candidate at all (D6).
8. An issue carrying `intent:new` alongside its status label loses `intent:new` in the same `gh issue edit` as the status swap; an issue already at the target label but still carrying `intent:new` still loses it; a Draft spec merge removes nothing. `grep -c 'status:planning' scripts/ci/lifecycle_advance.sh` is 0 and `scripts/ops/work.sh` is byte-unchanged in the diff (D7, D14).
9. The review row is a no-op in both directions: with the fixture patched so review's `advances_on` is `"merge"`, a merge candidate at `status:in-review` writes no label and posts no comment, and the strings `--add-label null` and `null` as a message body appear nowhere in the output (D8, D10).
10. `.github/workflows/lifecycle.yml` differs from `main` only inside its `permissions:` block, which reads `issues: write`, `contents: read`, `pull-requests: read`; the file contains no `pull_request:` trigger and no `secrets.` reference (D3).
11. Every transition comment carries the new `COMMENT_HEADER`, no comment anywhere in the suite contains the string "get their writers with #8/#9", and a merge candidate's body contains `Trigger: pull request #` while an artifact candidate's contains `added in` (D11).
12. `docs/SPEC.md` `lifecycle.labels` and `personas.resume` each changed in place with a `(PR #<n>)` citation, the string "their writers arrive with #8/#9" is gone from the file, `personas.resume`'s key list contains `advances_on`, and the section count of `docs/SPEC.md` is unchanged (D12).
13. `bash scripts/ci/tests/lifecycle_advance_test.sh` passes with an empty write log; `bash -n scripts/ci/lifecycle_advance.sh`, `bash scripts/ci/spec_check.sh origin/main`, `bash scripts/ci/sanitize_check.sh` and `python3 scripts/sync_agents.py --check` all exit 0 with no compiled target in the diff (D13, D14).
14. End to end on a real item: after the implementing pull request for one issue merges, that issue carries exactly one `status:*` label, `status:in-review`, carries no `intent:new`, and `DRY_RUN=1 scripts/ops/work.sh <n> --as argus` resolves to the review rung and exits 0 (D1, D7, D8).

## Out of scope

- **`review:1`/`review:2`/`review:3` and `status:review-stuck`** stay with #8 and #9. They are review state, not stage state; an advancer that guessed at them would be the second state machine the script header refuses to become (D8).
- **The review pipelines themselves** — Argus's workflow, Atlas's sidecar, consensus — are #8/#9 and depend on #25 for where a model runs. This change gives them a `status:in-review` they no longer have to write, and needs nothing from them.
- **#52's AT-3**, source validation of `personas/lifecycle.json` in `scripts/sync_agents.py --check`, stays on #52, which stays open. D10 adds `advances_on` to what that validator will need to cover (D10).
- **`scripts/ops/work.sh`, `scripts/sync_agents.py` and `scripts/auth/**`** are #43's this week. Everything this change needs from the dispatcher is a consequence of the label it writes, not an edit to that script (D14).
- **`scripts/ops/post.sh`**, the single hold-checked write path named by #25's merged plan (T7), is unbuilt. This change keeps posting through the advancer's existing `post_comment`/`edit_labels` wrappers and takes no dependency on it; when `post.sh` exists, those two wrappers are its natural adoption site.
- **Who closes a finished item, in automation.** D8 fixes that the ladder ends at review and the human closes; building anything that closes issues is neither proposed nor tracked here.
